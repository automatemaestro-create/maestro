# Maestro — Instructions pour Claude Code

Monorepo en phase de cadrage (Phase 0 — POC, voir [docs/06-roadmap.md](./docs/06-roadmap.md)). Squelette de dossiers en place (`apps/`, `core/`, `agents/`, `packages/`, `infra/`), pas encore de code applicatif. CI en place : [`.github/workflows/ci.yml`](./.github/workflows/ci.yml) joue six jobs sur les exécutants hébergés de GitHub — un pipeline vert est requis avant merge. **La CI ne se déclenche que sur les Pull Requests** ([docs/10 §8](./docs/10-workflow-git.md)) : ni au push sur une branche sans PR, ni sur `main` après le merge — avant la PR, on se vérifie en local avec `bash scripts/ci/local.sh`, qui **ne joue par défaut que les tests concernés par le diff** (#214, [docs/10 §8.4](./docs/10-workflow-git.md)).

## Règles Git obligatoires

- **Jamais de commit direct sur `main`.** Toujours travailler sur une branche de ticket.
- **Un ticket = une branche = une Pull Request.**
- Nommage de branche : `<type>/<iid>-<slug>` (ex. `feat/6-boucle-orchestration`). Le `type` vient du label `type::*` du ticket (`feature`→`feat`, `bug`→`fix`, `infra`→`chore`, `doc`→`docs`).
- Convention de commit : Conventional Commits + `Refs #<iid>` sur les commits intermédiaires, `Closes #<iid>` sur le commit final ou la description de la PR.
- **La clôture du travail passe par les skills dédiés** : `/ticket-ship` (commit auto + push + PR + statut) quand le travail est terminé, ou `/ticket-finish` si le commit est déjà fait. Ne jamais ré-implémenter ce cycle à la main (`git commit`/`git push`/`gh pr create` directs hors de ces commandes) — les skills en sont la source unique.
- **Découpage en sous-tickets & tests différés** ([docs/10 §5.1](./docs/10-workflow-git.md)) : un ticket = ~1 session de travail. La taille s'évalue en **charge estimée** sur **toute la description** (notes techniques et références croisées comprises) ; les **couches/composants** touchés sont un **signal** qui oblige à estimer finement, **pas un déclencheur automatique** (étalon : #48, trois couches substantielles ⇒ découpage ; un script + sa doc = 1 session ⇒ ticket unique). **Sous le seuil, pas de parent** : un besoin multi-facettes tenant en une session reste un **ticket unique**, au besoin avec une checklist interne dans sa description. Au-delà d'une session : **parent de suivi** (section `## Sous-tickets`, checklist ordonnée ; il ne se ferme que toutes cases cochées, fermeture humaine/orchestrateur) + **sous-tickets liés** (1-3 critères chacun, chacun mergeable seul sur `main` sans casser l'existant, description commençant par `Sous-ticket de #<parent>`). Les lots s'enchaînent **sans attendre le merge** du précédent : « En revue » suffit, seul un lot encore « À faire »/« En cours » bloque. **Lots parallélisables** : un lot dont le titre dans la checklist du parent se termine par **`(parallèle)`** ne dépend pas des autres lots marqués qui le précèdent — deux personnes peuvent les prendre en même temps. Marqueur facultatif (sans lui, séquentiel comme avant) ; un lot **non marqué** reste barré par tout ce qui le précède, ce qui garde le lot final « tests + doc » (jamais marqué) derrière l'ensemble. Les **tests sont différés au lot final « tests + doc »** ; un lot intermédiaire n'en porte que si sa logique est critique et référence « Tests différés → #<iid> ». Helpers : `lib.sh issue-link`/`parent-of`/`subtickets`/`startables`.
- Détail complet : [docs/10-workflow-git.md](./docs/10-workflow-git.md).

## Cycle de vie & labels (déjà en place — ne pas en réinventer d'autres)

Le **cycle de vie** d'un ticket est porté par le champ **Status** du projet GitHub Projects v2, qui
en est le **seul support** depuis que #365 a retiré les six labels `workflow::*` et le commutateur
`MAESTRO_CYCLE` ([docs/10 §3.1](./docs/10-workflow-git.md)).
Ses six valeurs sont les **libellés** de toujours — « À faire / En cours / En revue / Terminé /
Abandonné / Doublon » — et le vocabulaire n'a pas bougé d'un caractère : les commandes `/ticket-*`
le posent via `lib.sh set-workflow <iid> "<libellé>"`, en entrée le slug (`en-cours`) est accepté
aussi, en sortie `lib.sh` ne rend **que** le libellé. Le projet se résout **par son titre**
(`MAESTRO_PROJECT_TITRE`, défaut « Maestro ») — aucun identifiant de projet, de champ ni d'option
n'est figé dans le dépôt.

⚠ **La panne a changé de forme : le Status vit sur l'ITEM de projet, pas sur l'issue.** Un ticket
absent du projet n'a donc **aucun état**, et rien à l'écran ne l'y distingue d'un ticket filtré.
`/ticket-create` l'y ajoute dans la foulée de la création (#361), `doctor.sh` signale ce qui manque
(#363) et `lib.sh project-add <iid> "<état>"` répare, ticket par ticket — c'est le seul verbe de
peuplement depuis que le backfill est parti avec les labels (il dérivait le Status du label courant,
et de rien d'autre). En revanche l'**exclusion mutuelle n'est plus à notre charge** — un champ à
valeur unique rend « deux états à la fois » impossible par construction, et c'est tout le gain du
chantier #358.

⚠ **Il n'y a plus de retour arrière, et c'est la décision de #365.** Tant que les six labels
`workflow::*` étaient là, rebasculer coûtait un `MAESTRO_CYCLE=labels` ; ils sont partis avec le
commutateur, le backend qui les servait et leur provisionnement, donc rebasculer coûterait une
migration. Ne pas réintroduire un second support « au cas où » : c'est exactement ce que ce chantier
a supprimé, et le premier symptôme de deux supports est un ticket qui porte deux états. Qui veut
l'état lit `lib.sh backlog-table` ou `issue-owner` — `lib.sh backlog` (le JSON brut) n'en porte
aucun, l'état ne vivant pas sur l'issue.

⚠ **Ce n'est pas un retour à #12/#13, et ça ne défait pas #207.** Le cycle de vie a été porté par un
champ Status natif du temps de GitLab (#12/#13), fonctionnalité **Premium** perdue à la fin de
l'essai Ultimate le 2026-08-02 — d'où le repli sur les labels (#207), qui n'était pas un choix mais
le seul mécanisme que GitLab Free laissait. La migration vers GitHub (#335/#343) a rendu disponible
ce qui manquait alors : Projects v2 offre le champ **gratuitement**, dépôt privé compris. #358
remplace donc #207 par ce dont il avait été privé — ne pas le relire comme une hésitation.

Le dispositif est **gardé par [`tests/test_cycle_de_vie.py`](./tests/test_cycle_de_vie.py)** (#366,
[docs/10 §3.9](./docs/10-workflow-git.md)) : les six options dans l'ordre du flux et l'idempotence du
monteur, l'aller-retour libellé → option → libellé sur les six états, l'asymétrie écriture/lecture
d'un ticket hors projet, le recouvrement des tables par la carte et sa péremption à l'écriture, les
dérives de `doctor.sh`. Trois de ses contrôles sont des **`grep` sur le dépôt** — aucun identifiant
Projects v2 figé, aucun label `workflow::` survivant, aucun commutateur `MAESTRO_CYCLE` — et chacun
**prouve son motif** sur un échantillon fautif avant de balayer : c'est ce qui les distingue d'un ✓
sur une question jamais posée. Deux exclusions qui n'en sont pas : `scripts/migration/` nomme les six
labels parce qu'il lit l'**archive** GitLab, et les fichiers qui racontent le retrait le mentionnent
au passé — le motif cherche un **usage**, jamais une mention. Le harnais (dépôt jetable + `gh`
factice) est partagé avec `tests/test_collaboration.py` dans
[`tests/harnais_forge.py`](./tests/harnais_forge.py) : deux doubles à tenir d'accord seraient le
premier moyen de rendre une suite verte sur une forme de réponse que l'autre a corrigée depuis.

Les **autres labels** ne servent qu'à catégoriser : **`type::`** (`feature`/`bug`/`doc`/`infra`),
**`agent::`** (`dev`/`bdd`/`devops`/`design`/`qa`/`orchestrateur`) et **`prio::`**
(`haute`/`moyenne`/`basse`) — tous en français. Ne pas recréer de
`status::*`/`priority::*`/`type::docs`/`type::chore` en anglais.

## Commandes disponibles

- `/setup` — **met en route un clone** : appelle `scripts/setup.sh` (prérequis, `.venv`, `.env`, hooks git, `apps/web`, réglages MCP locaux, Docker + runner CI de la machine) et prend en charge ce que le script ne peut pas faire seul — authentifications interactives, diagnostic d'une étape en échec, accompagnement du remplissage du `.env`. Ne réimplémente jamais les étapes à la main : le script en est la source unique.
- `/ticket-create <type> <titre>` — crée un ticket bien formé (corps de template + labels `type::`/`agent::`/`prio::` + **milestone de la phase courante** — milestone actif le plus ancien non soldé, `lib.sh current-milestone`, docs/10 §3.4) + **l'état « À faire »** posé dans le même geste — le ticket est **ajouté au projet** et son champ Status renseigné (#361), rien côté forge ne le faisant à notre place. **Évalue la taille** : au-delà d'~1 session, crée un **parent de suivi + sous-tickets liés** (découpage, docs/10 §5.1) ; sinon ticket unique, avec checklist interne s'il est multi-facettes. Ne crée pas de branche (c'est le rôle de `/ticket-start`).
- `/ticket-start <iid>` — **monte le worktree du ticket et y relocalise la session** (#181 — `worktree.sh ensure` rend `WORKTREE <chemin>` → bascule via `EnterWorktree`, ou `ICI <chemin>` → on y est déjà, ce qui garde `orchestrate/run.sh` intact), crée la branche à partir du ticket, l'assigne, passe le **cycle de vie** à `En cours`, pose les **dates** (début = aujourd'hui, échéance = début + délai selon `prio::`), et **remet au passage le dépôt à niveau** : `main` avancée sur `origin/main` en fast-forward (`sync-main`, #205), worktrees soldés ramassés puis branches locales déjà mergées purgées (`cleanup-merged`, même garde-fou que `/branch-cleanup` — dans cet ordre, #305) et **dépendances du clone principal remises à niveau** quand le dépôt en a ajouté (#216 — détection et réparation déléguées à `setup.sh`, signalées, jamais bloquantes). **Le clone principal ne change donc plus de branche** : on peut y rester sur `main` pendant qu'un ticket tourne. Deux corollaires : un arbre non propre n'est plus un refus mais un **signalement** (le travail part ailleurs — bloquant seulement si le verdict est `ICI`), et la relocalisation déplace le répertoire de travail **mais pas le bloc `env`** (ports Control Tower et profil de navigateur restent ceux du clone principal — `ensure` affiche les bonnes valeurs, docs/10 §9.1). Puis **enchaîne directement sur l'implémentation** : le résumé de cadrage n'est pas une pause d'autorisation, aucun « go » n'est attendu. Cas particuliers (docs/10 §5.1) : sur un ticket **trop gros** (charge estimée > ~1 session), propose le découpage au lieu d'enchaîner ; sur un **parent de suivi**, redirige vers le premier lot « À faire » en sautant les lots livrés (« Terminé »/« En revue ») et ne s'arrête que sur un lot « En cours » ; sur un **sous-ticket**, vérifie que les lots précédents sont livrés (« Terminé » ou « En revue » — une PR en attente de merge ne bloque pas).
- `/ticket-finish` — **refuse d'abord de clôturer un ticket qui n'est pas celui de la session** (`lib.sh close-guard`, voir Garde-fous). Puis, **avant de pousser**, signale si la branche a pris du **retard sur `origin/main`** (`lib.sh behind-main` : commits de retard + fichiers modifiés des deux côtés = conflit probable) et propose le rebase **sans jamais le faire lui-même** (un rebase appellerait un force-push, interdit) ; le verdict n'interrompt pas la clôture. Puis pousse la branche, ouvre/met à jour la PR (`Closes #<iid>`), **coche dans la checklist de la PR les cases qu'il a effectivement vérifiées** (conventions, tests/doc d'après le diff, pipeline verte — mise à jour idempotente, ne décoche jamais une case cochée par un humain), passe le **cycle de vie** à `En revue`, **ne pose aucun relecteur** (#196 — la désignation d'un relecteur est un geste humain ; `lib.sh set-reviewer` reste disponible pour une pose explicite, la visibilité des PR en attente étant portée par la file de revue de `/backlog`), et **estime automatiquement le temps passé** (jugement de l'agent sur la portée du travail) puis le loggue, sans confirmation.
- `/ticket-ship` — **clôture zéro friction** : depuis un ticket en cours, **commite d'office** les changements en attente (message Conventional Commits généré + `Closes #<iid>`, sans confirmation) puis enchaîne `/ticket-finish`. Refuse si l'arbre est vide ou en conflit, jamais sur `main`, et **jamais sur un ticket que la session ne traite pas** (`lib.sh close-guard` **avant le commit** : le message porte `Closes #<iid>` et fermerait sinon le ticket d'un autre au merge). Pour un **sous-ticket**, annonce le prochain lot du parent, démarrable dès maintenant sans attendre le merge (ou que le parent est fermable si c'était le dernier), et synchronise la checklist du parent. À utiliser quand le travail est terminé et qu'on veut clore en une seule action ; `/ticket-finish` reste le choix si le commit est déjà fait.
- `/mr-fix [mr|branche]` — **rend une PR mergeable**, une PR à la fois (#303, [docs/10 §8.3](./docs/10-workflow-git.md) ; anciennement `/pipeline-fix`, qui ne traitait que la moitié du problème). Deux blocages, **dans cet ordre** : le **conflit avec `origin/main`** puis le **pipeline rouge**. L'ordre est le contenu de la décision — le merge d'`origin/main` peut *lui-même* casser le pipeline (deux changements corrects séparément, faux ensemble), donc diagnostiquer avant, c'est diagnostiquer un état qui n'existera plus. Le conflit se juge par `lib.sh mr-conflict` (`git merge-tree --write-tree`, un **merge 3-way réel** en lecture seule, jouable sur une branche qu'on ne sort pas) et **non** par les deux sources déjà là, dont aucune ne pouvait porter la décision : `behind-main` est une heuristique de fichiers **pessimiste** — vraie presque partout sur les fichiers aimants du dépôt, où les deux côtés éditent des régions disjointes — et répond en plus *avant le push*, quand le conflit naît des merges qui suivent ; le `has_conflicts` de GitLab est **asynchrone** (5 MR sur 6 en `checking`/`unchecked` à la mesure du 2026-08-07), à lire en complément et jamais à attendre. La résolution est un **merge, jamais un rebase** (un rebase appellerait un force-push, interdit), et une résolution qui n'est pas claire **ne se pousse pas** : `git merge --abort`, branche intacte, constat rendu. Côté pipeline, inchangé : jobs rouges + traces via `lib.sh`, correctif local quand c'est corrigeable (lint/test/typage), commit (`Refs #<iid>`), push, re-déclenchement si besoin (`gh run rerun <run-id>`, ou `gh workflow run ci.yml --ref <branche>` si le push n'a rien déclenché), verdict suivi (2 tentatives max) ; échec d'infra (secret manquant, flaky) : le dit et propose au plus `gh run rerun --failed <run-id>`. Le **résumé rend les deux blocages séparément**, jamais un ✅ global — c'est le faux verdict que le ticket a supprimé. Un piège à connaître : `git merge-tree` rend **`128`** et non `1` quand le merge est impossible à évaluer (histoires sans ancêtre commun) ; les confondre enverrait résoudre un merge qui ne peut pas avoir lieu. Ne touche jamais au cycle de vie (ni champ Status, ni PR, ni merge) et jamais de commit sur `main`.
- `/branch-cleanup` — après merge d'une PR : supprime la branche locale (par `lib.sh cleanup-merged`, #309 — la boucle « quel est l'état de la PR de cette branche ? » n'est plus décrite en prose, elle réinjectait ~43 000 tokens de JSON par invocation ; il ne reste autour du helper que ce qu'il ne fait pas) + distante, remet `main` à jour (`lib.sh sync-main`, #205 — fonctionne aussi depuis un worktree, où un `git checkout main` échouerait), pose le **cycle de vie** `Terminé`. Depuis #275 ce n'est plus le **seul** moment où il est posé : le merge ferme toujours le ticket sans toucher à aucun label, mais le ramassage des worktrees (`worktree.sh gc`, §9.2) pose « Terminé » sur le verdict « soldé » qu'il obtient déjà — donc à tout `/ticket-start`, à tout `/branch-cleanup` et au démarrage d'un run. La commande reste le geste explicite d'après-merge ; la pose y est devenue idempotente. **Et depuis #377 elle n'attend plus personne** ([docs/10 §9.2](./docs/10-workflow-git.md)) : un workflow GitHub Actions sur `issues: closed` ([`.github/workflows/cycle-de-vie.yml`](./.github/workflows/cycle-de-vie.yml) → [`scripts/github/ticket-ferme.sh`](./scripts/github/ticket-ferme.sh) → le même `reconcile-workflow`) la pose **à l'événement**, quels que soient l'auteur du merge et la machine — ce qui fait de `gc` un **filet** et non le seul mécanisme.
- `/ticket-abandon <iid> [doublon]` — clôt un ticket sans le réaliser : cycle de vie `Abandonné` (won't-do) ou `Doublon`, raison consignée, ticket fermé.
- `/orchestrate [--dry-run|--status|--resume [<run-id>]]` — **traitement autonome du backlog** ([docs/10 §11](./docs/10-workflow-git.md)) : les tickets « À faire » du milestone courant, un par un, chacun dans **son worktree** et **sa session Claude Code**, de `/ticket-start` à `/ticket-ship` — avec **reprise automatique** après la limite d'usage de 5 h. **Un seul run à la fois** (#213, [§11.9](./docs/10-workflow-git.md)) : démarrer comme reprendre commence par **tuer les runs encore en vol**, ce que la commande annonce avec le feu vert plutôt que de le laisser découvrir dans la console. La commande prépare, explique, lance et relit un run. **Au lancement, elle propose d'elle-même de reprendre** un run qui ne s'est pas terminé (#204, [§11.8](./docs/10-workflow-git.md)) : le choix « reprendre / nouveau run » remplace alors le feu vert, et aucune commande shell n'est à retenir — sans argument, `--resume` prend le run reprenable le plus récent. Pour un run **neuf**, elle propose aussi **le milestone** (`queue.sh --milestones`, [§11.2](./docs/10-workflow-git.md)) au lieu de prendre la phase courante en silence — mais seulement si le choix est réel : un seul milestone candidat s'annonce sans question. Le **pilote est toujours un script shell**, jamais une session Claude Code ni un travail d'arrière-plan de session — l'un consommerait le même quota que le travail piloté, l'autre mourrait avec la session. D'où `--detach`, qui relance le script dans une **console indépendante** et rend la main : c'est ainsi qu'un run se démarre depuis une session, **après confirmation** (il ouvre N PR). Le **suivi** ne dépend pas de cette console : `scripts/orchestrate/status.sh` (one-shot ou `--watch`) dit où en est un run depuis n'importe quel terminal, et c'est sur lui que `--status` s'appuie. Un run produit N **PR en Draft** à relire : il ne merge, ne ferme et ne force-push jamais.

Commandes de **supervision** (lecture seule — n'écrivent jamais : ni cycle de vie, ni PR, ni merge) :

- `/backlog [opened|all]` — vue d'ensemble du backlog groupée par **cycle de vie**, avec `agent::`/`prio::` et ce qui attend une revue / est prêt à merger. En tête de sortie, la **file de revue** (`lib.sh review-queue`) : les PR ouvertes, **la plus ancienne d'abord**, avec leur ancienneté, leur pipeline et leur relecteur s'il en a été posé un à la main (aucun ne l'est automatiquement, #196) — la revue est **best-effort** (aucune approbation obligatoire), c'est la visibilité qui la déclenche.
- `/mr-review <mr|branche>` — synthèse d'une PR (état, aptitude au merge, pipeline, threads, diff) pour éclairer la **décision de merge humaine**. Ne merge jamais.
- `/milestone-presentation [milestone]` — **présentation HTML** des travaux d'un milestone (défaut : la phase courante ; un fragment de titre suffit, ex. `Phase 3`). Regroupe les tickets par **état** (Livré / En revue / En cours / À venir) puis par `type::`, et y joint des **captures de la Control Tower prises en direct**. Produit un fichier **autonome** `docs/presentations/<slug>.html` (CSS en ligne, images en base64) — il n'est pas commité, c'est une décision humaine. N'écrit rien côté GitLab.

## Outillage requis

**Onboarding humain : [`CONTRIBUTING.md`](./CONTRIBUTING.md)** — le mode d'emploi d'un nouvel arrivant en une page (`setup.sh` → ticket libre via `/backlog` → `/ticket-start` → `/ticket-ship`, qui relit, qui merge). C'est là qu'on renvoie une personne qui demande « par où je commence ? » : ce fichier-ci est écrit pour l'agent, [docs/10](./docs/10-workflow-git.md) est exhaustif. Il ne porte **aucune règle nouvelle** — toute évolution du workflow se répercute dans docs/10 d'abord, `CONTRIBUTING.md` n'en étant qu'un résumé.

**Travail à plusieurs (plusieurs personnes, plusieurs clones) : [docs/10 §10](./docs/10-workflow-git.md)** — synthèse du chantier #155, **aucune règle nouvelle** : passer à plusieurs ne change pas le workflow, il rend coûteux ce qui n'était qu'inconfortable. Un point d'entrée qui renvoie, cas par cas, au mécanisme qui le traite : worktree par session (§9), anti-collision au démarrage (§5), garde-fou de clôture (§6), lots `(parallèle)` (§5.1), alerte de retard sur `origin/main` (§6), revue best-effort outillée (§6), runner partagé permanent (§8.1), filet CI local (§8), secrets `[perso]`/`[partagé]` (§7.3). **Rien de bloquant** : ces mécanismes *disent*, la décision reste humaine — `behind-main`/`close-guard` rendent un code de retour lu et jamais fatal, la revue n'exige aucune approbation, et aucun relecteur n'est posé d'office (#196). Couvert par [`tests/test_collaboration.py`](./tests/test_collaboration.py), [`tests/test_env_pull.py`](./tests/test_env_pull.py) et [`tests/test_ci_local.py`](./tests/test_ci_local.py).

**Mise en route d'un clone : `bash scripts/setup.sh`** (ou la commande `/setup`) — **source unique** du parcours, idempotente et non destructive. Elle installe les prérequis manquants (Python 3.11+, Node 20+, git, `gh`), crée le `.venv` et ses dépendances, copie `.env.example` vers `.env` (jamais écrasé), active le hook `commit-msg`, installe `apps/web`, fusionne `.claude/settings.local.json` clé par clé et monte le runner CI de la machine. `--check` pour un diagnostic sans écriture, `--only`/`--skip` pour rejouer une étape, **`--derive` pour la seule question « ce clone a-t-il pris ce que le dépôt a ajouté ? »** (#216 — TSV lisible par un script, 0 = à jour / 3 = dérive, ni réseau ni écriture ; c'est ce sur quoi s'appuient `/ticket-start` pour réparer et le filet CI local pour signaler, [docs/10 §9.4](./docs/10-workflow-git.md)). Ne jamais réimplémenter ces étapes à la main. Ses invariants sont testés par [`tests/test_setup.py`](./tests/test_setup.py) (dépôt jetable, sans réseau ni Docker).

**Secrets partagés : `bash scripts/env-pull.sh`** — dans [`.env.example`](./.env.example), chaque clé porte un marqueur **`# [perso]`** (jeton nominatif, chemin de machine, service local — le seul geste manuel qui reste) ou **`# [partagé]`** (secret du projet, endpoint, espace de travail). Les clés partagées vivent dans les **variables CI/CD du projet GitLab**, pas dans un fil de discussion : le script complète le `.env` avec celles qui manquent, sans jamais écraser une valeur déjà posée, sans toucher aux clés `[perso]` et sans imprimer aucune valeur (`--check` pour un diagnostic, `--manquantes` pour la liste brute — c'est ce que l'étape `env` de `setup.sh` interroge pour proposer le script). Publier une valeur partagée est un geste de mainteneur, une fois : `gh variable set <CLÉ> --body <valeur>` — une **variable** Actions, jamais un **secret** (`gh secret set`), les secrets étant *write-only* et donc irrécupérables par le script. Ses quatre promesses (le gabarit fait foi, non destructif, aucune valeur imprimée, franc sur ce qu'il ne peut pas) sont testées par [`tests/test_env_pull.py`](./tests/test_env_pull.py).

**Environnement Python : toujours utiliser le venv du repo (`.venv/`).** Les dépendances (`claude-agent-sdk`, `pytest`…) n'y sont installées que là — pas dans le `python` système. Lancer toute commande Python via cet interpréteur : sous Windows `.venv/Scripts/python.exe` (ex. `.venv/Scripts/python.exe -m pytest`), sous Unix `.venv/bin/python`. Avec le `python` système, la collecte des tests échoue dès l'import (`ModuleNotFoundError: No module named 'claude_agent_sdk'`).

**Ne rejoue pas la suite complète pendant le développement** (#214, [docs/10 §8.4](./docs/10-workflow-git.md)) — c'est le pipeline de la PR qui la joue, et depuis #165 il en est le seul verdict complet. **Le job `pytest` du filet joue dans un conteneur Linux** (#372, [docs/10 §8.4](./docs/10-workflow-git.md)) — les suites d'outillage sont faites à 100 % de sous-processus shell, or un fork coûte **~800 ms sous Windows contre < 1 ms sous Linux** : `tests/test_worktree.py` passe de 424 s à 13,5 s (×31), les six suites du périmètre `scripts/**` de 14 min 33 à 52,9 s, et la suite **entière** tient en 1 min 51. Le second gain n'est pas de vitesse et compte davantage : le filet joue enfin **sur l'OS du verdict**, donc voit la classe d'écart qui n'apparaissait qu'au merge (#332/#333 — 16 rouges d'un coup au premier runner Linux, dont un bug de production). Sans démon Docker il **retombe en natif et le dit** (deux fois : ligne du job et bloc avant le verdict) — un repli silencieux rendrait un vert de quinze minutes en se faisant passer pour un vert d'une minute ; `--conteneur` **échoue** au lieu de retomber, `--natif` force l'ancien régime. ⚠ **Mais « pas de démon » et « pas de Docker » ne sont plus la même chose** (#425, [docs/10 §8.4](./docs/10-workflow-git.md)) : ce repli a été écrit pour les postes **sans** Docker, et le cas courant en est un autre — Docker Desktop **installé, simplement pas démarré** —, qui empruntait le même chemin et payait le même prix (×15 à ×30, et un verdict aveugle aux écarts Windows/Linux) pour une cause qui se répare en une commande. Le filet **démarre donc Docker Desktop lui-même** avant de conclure au repli, en l'annonçant (35 s sur le poste de référence, démon froid). Ce qui sépare les deux situations est la présence du plugin **`docker desktop`**, livré avec Docker Desktop : absent, rien n'est tenté, aucun délai n'est payé et le repli garde exactement le comportement pour lequel il existe. Trois choix à ne pas défaire : la décision vit dans la **plomberie partagée**, donc `pytest.sh` en hérite sans une ligne ; la **sonde reste gratuite** (`--list` annonce « conteneur — après démarrage de Docker Desktop » sans rien démarrer, au même titre qu'elle ne construit jamais l'image) ; et un démarrage **en échec** nomme sa cause et retombe en natif au lieu de bloquer un verdict. `MAESTRO_DOCKER_DEMARRAGE=0` l'éteint, `MAESTRO_DOCKER_DEMARRAGE_DELAI` déplace le plafond (180 s). L'image est décrite par [`scripts/ci/pytest.Dockerfile`](./scripts/ci/pytest.Dockerfile), **versionné**, et son étiquette porte l'empreinte de `pyproject.toml` **et** du Dockerfile : une dépendance ajoutée au dépôt change l'étiquette, donc l'image manque, donc elle est reconstruite — personne n'a à s'en souvenir. Quatre choix à ne pas défaire : le dépôt est **monté et jamais à la racine** (monté à `/w`, son parent est `/` et `test_projets.py::test_depot_maestro_refuse` rougit pour une raison qui n'est pas la sienne — c'est `/maestro/depot`) ; l'image part de `python:3.11` **pleine** et **sans identité git globale**, les deux moitiés indissociables de #333 ; elle installe un paquet **vide** puis en **efface les sources** (sans le désinstaller — `[project.scripts]` déclare une dizaine de points d'entrée dont `tests/test_isolation.py` exige la présence), si bien que `import maestro` n'a plus qu'une source — le dépôt monté —, ce qui rend la question de #194 sans objet plutôt que résolue ; et les tests n'ouvrent **aucun conteneur**, c'est le `docker` neutralisé de la fixture qui répond, sans quoi les shims du `PATH` ne franchiraient pas la frontière. `MAESTRO_PYTEST_REGIME=auto|conteneur|natif`. `bash scripts/ci/local.sh` ne joue par défaut que les **suites concernées par le diff** (lint toujours complet, seuil de couverture non appliqué, verdict annoncé « Périmètre réduit ») ; `--complet` rejoue tout. Le périmètre se déduit fichier par fichier : `maestro/**` → les suites **applicatives**, `scripts/**`/`.claude/**`/`.github/**` → les suites qui **nomment** le fichier, `tests/test_*.py` → elles-mêmes, `conftest.py`/`pyproject.toml`/**tout chemin non classé** → la suite entière, `docs/**` et `apps/web/**` → rien côté pytest. Deux invariants à ne pas défaire : les suites d'**outillage** sont **dérivées** (une suite est « outillage » si elle nomme un script du dépôt — donc une suite nouvelle qui n'en nomme aucun est applicative, jamais sautée en silence), et on **n'affine pas à l'intérieur de `maestro/`** (le couplage entre modules est invisible d'une recherche textuelle : toutes les suites applicatives, 40 s, aucun faux négatif). **Pour une itération serrée, le lanceur `bash scripts/ci/pytest.sh <arguments pytest>`** (#405, [docs/10 §8.4bis](./docs/10-workflow-git.md)) joue une **cible** — suite, nodeid, `-k` — dans le même conteneur, ce que le filet ne permettait pas, son périmètre étant déduit du diff : `tests/test_cycle_de_vie.py` passe de **~8 min** en natif à **21 s** (×18, mesuré le 2026-08-21). ⚠ Le conteneur n'est pas meilleur partout, et c'est la nuance que cette ligne taisait : on **tranche par famille de suite** — une suite d'**outillage** (celle qui **nomme un script** du dépôt, même dérivation que le périmètre ci-dessus) y gagne un facteur vingt ; une suite **applicative** n'y gagne rien (`tests/test_engine.py` : 6,3 s en natif contre ~6 s de seul démarrage + montage), donc `.venv/Scripts/python.exe -m pytest tests/test_engine.py` y reste la bonne réponse. La plomberie est **partagée** et non recopiée ([`scripts/ci/pytest-regime.sh`](./scripts/ci/pytest-regime.sh), sourcé par le filet **et** le lanceur) — deux implémentations à tenir d'accord seraient le premier moyen pour qu'un lanceur cesse d'exécuter ce que le filet prédit, et `tests/test_ci_local.py` garde qu'aucune de ses fonctions n'existe en double. Trois comportements à connaître : le parallélisme est ajouté d'office **dans le conteneur et jamais en natif** — c'est la règle déjà écrite pour le filet (démarrer les workers coûte ~5,5 s, plus qu'une suite applicative ciblée), **mesurée** ici à 6,3 s en série contre **37,5 s à `-n 8`** sur `tests/test_engine.py`, soit six fois plus lent sur le cas même qu'il devait servir — et jamais non plus contre un choix explicite (`-n`, `-p no:xdist`) ni contre une intention de **regarder** tourner (`--pdb`, `-s`, `--capture=no`), que xdist vide de leur sens **sans que pytest s'en plaigne** ; sans argument il rend l'**aide** au lieu de collecter toute la suite ; et il **dit où il joue avant de jouer**, `--conteneur`/`--natif` forçant l'un ou l'autre (un repli **subi** nomme sa cause, un `--natif` **voulu** s'annonce sobrement — avertir d'un facteur vingt qui ne concerne pas son cas apprend à ne plus lire les avertissements). Ce n'est **pas un verdict** : avant de pousser, c'est toujours `bash scripts/ci/local.sh`. **Les deux commandes qui vérifient en local y renvoient** (#310) au lieu de porter leur propre recette : `/mr-fix` rejoue le job rouge par `bash scripts/ci/local.sh --only <job>` et `/ticket-finish` passe le filet avant de pousser. Ce n'est pas qu'une économie de mots — la table de miroirs de `/mr-fix` prescrivait `pytest -n auto` sur la suite entière, soit l'inverse de cette règle-ci, et un prompt est ce que la session lit en dernier : c'est lui qui l'emporte. Une recette recopiée dans un prompt fige les jobs de `.github/workflows/ci.yml` au jour où elle a été écrite ; `tests/test_ci_local.py` garde qu'aucun bloc de code ni tableau de `.claude/**` n'en réintroduise une. Le parallélisme (`pytest-xdist`) est acquis côté CI en `-n auto` (1 min 53 s au lieu de ~10) et n'est passé en local que quand une suite d'outillage est dans le périmètre : démarrer les workers coûte ~5,5 s, soit plus qu'une suite applicative ciblée. En **régime natif** il est **plafonné à `min(cœurs, 8)`** (#285, [docs/10 §8.4](./docs/10-workflow-git.md)) — la contrainte est la **mémoire** et non les cœurs (~130 Mo par worker, ~2 Go à seize pour ~1,8 Go libres), si bien que `-n auto` et `-n 8` sont à égalité pour deux fois moins de processus. ⚠ Ce plafond est un fait sur la **mémoire du poste Windows**, jamais un fait sur pytest : **dans le conteneur il disparaît** au profit de `-n auto`, le drapeau même de la CI (#372 — re-mesuré sur les six suites du périmètre, 598 tests : `-n 4` 177 s · `-n 8` 63 s · `-n 16` 56 s · `-n auto` 46 s, **tous verts**, là où `-n 16` sous Windows faisait *pire* que `-n 8` — 11 min 37 — **et** rougissait quatre tests de la vue console par saturation). `MAESTRO_PYTEST_WORKERS` déplace le plafond des deux côtés. Le **lint shellcheck, lui, s'appelle fichier par fichier des DEUX côtés** — filet et `.github/workflows/ci.yml` (53 s → 16 s) : shellcheck est superlinéaire en taille totale reçue d'un coup, mais il ne suit un `# shellcheck source=` que si le fichier sourcé est **lui aussi sur la ligne de commande**, donc découper d'un seul côté rendrait le filet plus strict que la CI qu'il prédit. Un couplage entre scripts se déclare désormais sur place par un `# shellcheck disable=` commenté ; `-x` le rétablirait mais annule le gain (34 s, mesuré). **Le journal d'un job rouge se lit sur place** (#234, [docs/10 §8.5](./docs/10-workflow-git.md)) : il est écrit sous `<racine>/.maestro/ci-local/<job>.log` et le chemin affiché est **relatif** — un chemin absolu hors du répertoire de travail demanderait une approbation qu'une session autonome n'a personne pour donner, et le run de #200 y a laissé 13 refus sans jamais lire pourquoi ses tests échouaient. La règle vaut pour tout le dépôt : **ce qu'un script invite à lire** va sous `.maestro/<domaine>/` (gitignoré, table rase à chaque lancement pour le filet) ; **ce que personne ne lit** — brouillons, profils jetables, caches d'installation, fichiers porteurs de secrets — reste dans `${TMPDIR:-/tmp}`, avec en commentaire la raison de son maintien, pour que l'audit (`grep -rn "TMPDIR\|/tmp" scripts/`) soit une relecture et non une réenquête.

**Suite pytest : aucun test n'a besoin d'un backend, et [`tests/conftest.py`](./tests/conftest.py) l'impose** (#195, [docs/10 §8](./docs/10-workflow-git.md)) — pendant Python du réseau débranché côté `apps/web`. Il vide les **clés Langfuse** de l'environnement du processus de test et **échoue le test** qui laisse un `LangfuseExportHandler` sur le logger global `maestro.trace`. Motif à connaître avant d'ajouter un handler à un logger de `maestro.` : `activer_export_langfuse()` est appelée par **chaque** point d'entrée (`engine_cli.main`, `maestro.demo.main`) et rien ne la retire, donc elle est **idempotente** — sans quoi N invocations dans un même processus accrochaient N handlers, et chaque ligne journalisée partait N fois en POST **synchrone** (traces et coûts dupliqués en production ; 17 min 51 s de suite pytest au lieu de 7 min 08 s sur un poste aux clés renseignées). Il neutralise aussi **`MAESTRO_ORCHESTRATE_COULEUR`** (#236), qu'un bloc `env` de `.claude/settings.local.json` fait fuiter dans les sous-processus de `tests/test_orchestrate.py` — sortie colorée, `test_sans_le_marqueur_la_sortie_reste_sans_couleur` rouge **en local seulement**, quatre sessions parties enquêter sur une fausse alerte. Règle générale dont ce sont deux cas : **le verdict de la suite ne dépend pas du poste** — une variable qui fuit se neutralise dans le conftest, jamais en la retirant du `settings.local.json` d'un poste (non versionné, le prochain clone la repose). Le quatrième garde-fou est le seul qui **refuse de jouer** au lieu de neutraliser (#333, [docs/10 §8.7](./docs/10-workflow-git.md)) : les trois premiers protègent le verdict de ce que le poste apporte **en trop**, celui-ci de ce que l'image du job **n'apporte pas**. Le job `pytest` tourne dans `python:3.11-slim`, **qui n'a pas git**, et sept modules d'outillage sont gardés par `skipif(shutil.which("git") is None)` : **285 tests étaient sautés à chaque pipeline**, sans que rien ne distingue ce vert-là d'un vert complet — si bien qu'ils n'ont jamais tourné **que sous Windows**, et que le premier runner Linux muni de git en a trouvé **16 rouges d'un coup** (#332), dont un bug de production (la fusion de `maestro/projets/application.py` n'échouait que sur les machines sans `~/.gitconfig`, c'est-à-dire nulle part où quelqu'un regardait). Deux moitiés indissociables : git est **présent** dans le job — par l'**image pleine** `python:3.11` et non par un `apt-get install git`, essayé puis retiré parce qu'il met une dépendance réseau aux miroirs Debian dans chaque pipeline, sur le chemin critique du merge (le pipeline de !269 est mort dessus, « Unable to connect to deb.debian.org », avant même que pytest démarre : un remède qui coûte une panne récurrente n'en est pas un) —, et **sans identité globale**, en poser une remasquerait exactement ce bug ; et son absence **en CI** (`CI`/`GITLAB_CI`/`GITHUB_ACTIONS` posée) est une **erreur franche** levée avant la collecte. Sur un poste sans git, le `skipif` reste la bonne réponse : il dit « cette machine ne peut pas répondre », là où le même saut en CI dit « rien n'a été vérifié » avec les mots de « tout va bien ». Un garde-fou qui saute est plus dangereux qu'un garde-fou absent. Corollaire à connaître avant de toucher à quoi que ce soit de multi-plateforme : ces tests ne tournent **que sur Linux en CI et sur Windows en local**, donc un écart entre plateformes ne se voit qu'au croisement des deux — c'est ainsi qu'un `.venv/` du `.gitignore` (motif à barre finale, qui ne matche **que des répertoires**) ignorait la **jonction** Windows et laissait le **lien symbolique** Linux, salissant tout worktree neuf ([docs/10 §9](./docs/10-workflow-git.md)). Pour trancher ce genre de cause, rejouer la suite dans l'image du pipeline **avec git** (quelques lignes de Docker, jetables) vaut mieux que raisonner à distance.

**Environnement Node : la version est épinglée par le dépôt ([`.node-version`](./.node-version)), pas par le gestionnaire du poste.** `scripts/setup.sh` la provisionne sous `.tools/node/` (gitignoré, téléchargement vérifié par SHA-256, aucun droit admin) et la place en tête du `PATH` pour les étapes suivantes — un `nvm use 18` sur la machine ne casse donc plus rien. Le serveur MCP `chrome-maestro` passe par [`scripts/mcp/playwright-mcp.mjs`](./scripts/mcp/playwright-mcp.mjs), qui relance `@playwright/mcp` avec ce Node-là : Claude Code démarre ses serveurs avec le `PATH` de **son** processus, qu'aucun hook de shell (`.nvmrc`, fnm) n'atteint. Symptôme si ce maillon saute : le serveur ressort « not connected » sans message, `@playwright/mcp` exigeant Node ≥ 20. Reprovisionner : `bash scripts/setup.sh --only node`.

**Tests de l'UI Control Tower : `npm test` dans `apps/web`** (Vitest + Testing Library sur jsdom, posés par #124 ; `npm run test:watch` pendant le développement). Ils couvrent la refonte UX #116 — navigation, thème, notifications, identité, paramètres, visite guidée, assistant — et tournent dans le job CI `web-build` entre `npm run lint` et `npm run build`. Le réseau y est débranché d'office (`tests/setup.ts` mocke `useControlTower`/`useChat`) : **aucun test n'a besoin de backend**, et le bout en bout dans un vrai navigateur reste le rôle du skill `/verify`. **La mise en page, elle, n'appartient à aucun des deux** (#308) : jsdom ne calcule ni hauteur, ni `overflow`, ni défilement, et `/verify` regarde le câblage et non la géométrie — d'où le skill **`/banc-mise-en-page`**, à passer dès qu'un ticket porte sur des hauteurs, du défilement, des éléments collants ou du responsive. Il rend, pour une page donnée, les captures aux points de rupture, les débordements horizontaux et **ce qu'aucun défilement ne peut ramener** — la classe de bug de #306, que la suite verte, le lint, le typage et `next build` ont tous laissée passer. Détail : [`apps/web/README.md`](./apps/web/README.md#la-suite-de-tests).

**Boucle d'orchestration autonome : `scripts/orchestrate/`** ([docs/10 §11](./docs/10-workflow-git.md), parent #167) — `queue.sh` calcule **l'ordre de traitement, figé au départ** (parents de suivi écartés au profit de leurs lots, gardés contigus et dans l'ordre de la checklist) et, via `--milestones`, dit **sur quel milestone** un run peut porter (actifs seulement, comptés en « À faire » **et libres** — un milestone dont tout est assigné rendrait un plan vide) ; `run.sh` déroule le plan, **un worktree et une session par ticket**, et **reprend tout seul** après la limite d'usage (réouverture de la même session Claude, trois filets de détection, plafond à 5 h 30 au-delà duquel c'est l'hebdomadaire) ; le **régime des sessions est épinglé par le dépôt, pas par le poste** — modèle `claude-opus-5` (#206) et effort `xhigh` (#217), tous deux passés en toutes lettres au CLI et annoncés dans la ligne `plan :`, surchargeables par `--modele`/`--effort` (ou `MAESTRO_ORCHESTRATE_MODELE`/`_EFFORT`) : un réglage qu'on ne passe pas est un réglage que la machine choisit, et pour l'effort c'était `~/.claude/settings.json` qui décidait, `--settings` **ajoutant** une couche sans remplacer la chaîne (même mécanisme que l'union du `allow` ci-dessous) — d'où un clone traitant le backlog à l'effort par défaut, un `/effort` changeant le régime de toutes les sessions autonomes et des coûts non comparables d'une machine à l'autre, sans que rien ne le montre ; un niveau inconnu est refusé **avant** le premier ticket, l'effort étant un ensemble fermé de cinq valeurs là où un nom de modèle est une chaîne ouverte. Le troisième réglage du régime, le **plafond de dépense, ne s'applique plus par défaut** (#286, [docs/10 §11.3](./docs/10-workflow-git.md)) : `--max-budget-usd 15` partait à chaque session — garde-fou d'une boucle neuve, quand on craignait l'emballement —, mais une session qui touche le plafond est **tuée en plein travail**, sort sans commit ni PR, et compte pour un **échec**, ce qui saborde les lots suivants de son parent ; les deux runs du 2026-08-06 l'ont payé au même montant exact (#277 et #245 coupés à 15.07 $, 16 et 24 fichiers non commités, 13 lots sautés en cascade) pour zéro livrable. Un run reste borné par ce qui le borne vraiment — `STOP`, limite d'usage, plafond d'attente de 5 h 30 — ; `--budget <usd>`/`MAESTRO_ORCHESTRATE_BUDGET` restent là pour en **poser** un, `0` ou vide valant « aucun » (seule façon d'annuler une variable déjà posée, et le repli qui évite qu'un `--max-budget-usd 0` parte tuer chaque session), et le régime effectif est **annoncé dans les deux sens** — « budget illimité » ou « budget N $/ticket » — dans la ligne `plan :` comme dans `--dry-run`, illimité étant un choix et non un oubli. **Le quatrième réglage, le délai par ticket, a suivi le même sort** (#326, [docs/10 §11.3](./docs/10-workflow-git.md)) : `timeout 45m` enveloppait chaque session — large quand une session durait vingt minutes, devenu le **premier tueur de sessions du run** au régime `claude-opus-5` + `xhigh`. Mesuré le 2026-08-10 (run `20260810-141208`) : **#315 livré en 42 min 50** et **#316 coupé à 45 min 02** alors que son travail était **fini et commité** — le couperet est tombé pendant le push et l'ouverture de la PR, donc le plafond n'a rien protégé : un ticket livrable transformé en échec, puis **sept lots sautés** en cascade, pour un seul livrable à 14,75 $. Sans `--timeout`, plus aucune enveloppe ; `--timeout <durée>`/`MAESTRO_ORCHESTRATE_TIMEOUT` en posent une, `0` ou vide valant « aucun délai » (même repli que le budget — un `timeout 0` tuerait chaque session à l'instant même), et la ligne `plan :` annonce « sans délai » ou « timeout N/ticket ». Un point à connaître avant d'y toucher : l'**échéance que le pilote se donnait** par ticket en vol (`P_ECHEANCE`, filet contre un sous-shell emporté par un SIGKILL, qui ne laisse aucun témoin) se calculait à partir de ce délai — sans lui, **aucun plafond de remplacement n'a été inventé**, en poser un « raisonnable » recréerait le défaut qu'on vient de supprimer, côté pilote et sans raison lisible. **Un run peut mener N tickets de front** (#289, [docs/10 §11.10](./docs/10-workflow-git.md)) : `--concurrence <n>` (ou `MAESTRO_ORCHESTRATE_CONCURRENCE`), **défaut 1** — sans l'option le run est celui d'hier, séquentiel au bit près. L'indépendance n'est pas devinée par la boucle : elle est **lue dans le plan**, colonne `groupe` de `queue.sh` (#288, [§11.2](./docs/10-workflow-git.md)) — « parents différents, ou même groupe » —, la règle vivant à un seul endroit pour que deux formulations ne divergent pas. Un créneau qui se libère prend le prochain ticket **éligible** et non le suivant : un lot barré par son prédécesseur est enjambé au profit d'un ticket d'un autre parent, plus loin dans le plan. Le partage est celui entre **l'état du run** et **ce qui dure** : le pilote garde tout (plan, éligibilité, sauts, `--max`, cascade, compteurs, montage des worktrees, verdicts) et reste **seul à écrire `resume.tsv`** — ce qui règle par construction la question de l'atomicité d'une ligne, au lieu de la confier à un `>>` partagé dont la réponse dépendrait de la plateforme ; seule la **session** part dans un sous-shell, qui rend son code par un **témoin** (`<iid>.fini`, posé par un trap `EXIT`) faute de `wait` portable sachant dire *lequel* des enfants vient de finir. Le montage des worktrees est **sérialisé** à dessein (`git worktree add` verrouille des refs du dépôt partagé ; ~1 s de pré-vol par ticket, noyé dans une session d'une heure), et la **cascade d'échec se décide à la fin d'un ticket** et non à son tour de boucle — avec N en vol, le tour d'un lot peut précéder le verdict de son prédécesseur. Deux choses à savoir avant de s'en servir : toutes les sessions tirent sur le **même quota** (le gain est en temps de mur, jamais en quota) — la vue, elle, rend les N tickets en vol depuis #290, et chaque ligne de ticket du journal porte **son numéro** sans quoi rien ne dirait, dans une trace entrelacée, à qui appartient un « ✓ PR #99 ouverte » ; enfin un plan **antérieur à #288** (cinq colonnes, rejoué par `--resume`) retombe en séquentiel en le disant, et `--concurrence 0` est refusé avant le premier ticket. **Ce qui était vrai d'un seul ticket devient, à N, une propriété du run** (#291, [docs/10 §11.4/§11.8/§11.9](./docs/10-workflow-git.md)), et les trois mécanismes concernés étaient *faux* et pas seulement redondants. **La limite d'usage** tombe sur toutes les sessions à quelques secondes d'intervalle : elles se rangent donc derrière un **rendez-vous unique** (`<run-dir>/.limite` — fin d'attente, source `reset`/`palier`, iid de l'ouvreur) où **la meilleure information l'emporte, jamais la plus récente** — une heure de reset explicite remplace un palier aveugle **même plus tôt** (un palier n'est pas une promesse, c'est un aveu d'ignorance), à source égale on ne fait que **rallonger** (se réveiller avant le reset brûle une reprise sur une limite toujours en cours, et c'est exactement ce qui faisait sortir en échec la session la moins bien informée pendant que sa voisine repartait) ; la fin est **relue à chaque tranche**, chaque session coupée reste **rouverte par son propre uuid**, le pilote **ne lance rien** pendant une attente en cours (mais seulement si quelque chose est en vol — sinon il sortirait de sa boucle et le reste du plan finirait le run sans une ligne de bilan) et le plafond des 5 h 30 se déclare une fois pour tous (`.plafond`). Pas de verrou — `flock` n'existe pas sous MSYS —, la **création exclusive** (`set -C`) suffit à désigner un annonceur et une écriture perdue se répare d'elle-même. **L'arrêt** vise désormais **chaque cible par son propre WINPID, du plus profond au plus superficiel** : un `taskkill //T` sur le seul pilote construit l'arbre à partir des liens que Windows connaît *à cet instant*, et il suffit qu'un sous-shell soit déjà sorti pour que son `claude.exe` ne soit plus rattaché à rien d'atteignable — tuer un parent avant ses enfants est ce qui fabrique l'orphelin qu'on veut éviter ; le rapport nomme **tous** les tickets interrompus, et `STOP` garde son sens (il arrête de *lancer*, il ne tue personne). **La reprise**, enfin, rejoue **tous** les tickets en vol (la question est posée par ticket) **et la concurrence** du run coupé, relue dans son fichier `concurrence` : sans elle, `/orchestrate --resume`, qui ne passe aucune option, rejouerait en séquentiel un run qui tournait à quatre. `guard.sh` + `settings.run.json` gardent les `deny` du dépôt **actifs** — là où `--dangerously-skip-permissions` les neutraliserait — et refusent en dur, en hook `PreToolUse`, force-push, `gh pr merge`/`pr close`, `gh run delete` et tout commit sur `main`. L'`allow`, lui, se complète **à partir des refus observés** ([docs/10 §11.7](./docs/10-workflow-git.md)) : chaque session laisse dans `permission_denials` ce qu'elle n'a pas pu faire, et on l'instruit au cas par cas — le premier run réel y a laissé 17 refus (#179), dont le tool **`Skill`** — sans lui une session refait `/ticket-start` **à la main**, ce que ce fichier interdit. **Un refus ne s'instruit pas : écrire sous `.claude/`** (#229, **mesuré** par #238) — le blocage vient du CLI et non de la liste, il est **en amont** du `allow` et **déborde les outils de fichier** : ni une règle à chemin explicite (`Edit(.claude/skills/**)`, en relatif comme en absolu), ni un `cp` dont le CLI sait lire la cible ne le lèvent. Une session qui bute dessus **rend le contenu dans sa PR** (#188) au lieu de contourner, et un ticket touchant `.claude/**` se traite en session interactive dès le départ. Le banc qui l'établit est dans le dépôt et se rejoue : `.venv/Scripts/python.exe scripts/claude/essai-ecriture-claude.py` (tests : [`tests/test_essai_ecriture_claude.py`](./tests/test_essai_ecriture_claude.py)). Deux pièges à connaître avant d'élargir quoi que ce soit : une **commande composée vaut son maillon le plus faible** (le CLI découpe sur `&&`/`;`/`|` et exige chaque morceau — un `cd` ou un `echo` de confort fait tomber une chaîne par ailleurs autorisée), et l'**`allow` est l'union** de ce fichier et de `.claude/settings.json`, là où le `deny` est recopié à dessein. Une session appelle donc ses commandes **depuis son worktree, en chemins relatifs, une par une**. **Et depuis #307, ce n'est plus l'`allow` qu'il faut regarder en premier** ([docs/10 §11.7](./docs/10-workflow-git.md)) : `journal.sh refus` **classe** désormais chaque refus dans une seule famille — trou d'allowlist, échappée de chemin, blocage dur `.claude/`, refus voulu (`ask`/`deny`), forme immatchable — en rejouant les règles **là où elles vivent** (`settings.run.json` ∪ `.claude/settings.json`, jamais une copie qui se périmerait). Verdict du dernier run complet : **9 refus sur 12 (75 %) sont des échappées de chemin**, et les sept commandes les plus refusées du journal (`echo`, `cd`, `tail`, `cat`, `head`, `grep`, `sed`) sont **toutes déjà autorisées** — ce qui les fait tomber est la **cible**, qu'aucune règle de préfixe ne borne. D'où l'**atelier de session** : `worktree.sh` monte **`.maestro/session/`** dans chaque worktree (gitignoré) et le prompt l'y envoie, parce qu'interdire `/tmp` et le répertoire temporaire sans **désigner** un remplaçant ne fait que déplacer le refus — une session écrit forcément ses fichiers de travail quelque part. Même raison pour `journal.sh`, qui résout le journal vers le **clone principal** d'où qu'on le lise : sans ça, une session lisant ses propres refus depuis un worktree devait passer par un chemin absolu, et l'outil de mesure produisait le refus qu'il mesure. Deux corollaires à connaître : les règles lues sont celles **d'aujourd'hui**, donc sur un vieux run « inclassé » dit surtout « déjà instruit depuis » (c'est le **dernier** run qui se lit pour agir), et l'**ordre de décision** (`.claude/`, refus voulu, trou, chemin, forme) est le contenu du classement — on ne conclut à l'échappée que si rien d'autre n'explique le refus. Le seul vrai trou restant, le **préfixe de variable** `VAR=… <commande>`, a été **écarté** et non ajouté : une règle est un préfixe de *commande*, il faudrait donc figer la valeur en dur, et le geste existe déjà — **`env VAR=… <commande>`**, que `Bash(env:*)` couvre. **Le pilote est un script shell, jamais une session Claude Code** : une boucle en `/loop` ou en sous-agents consommerait le même quota que le travail piloté et mourrait avec lui. `run.sh --detach` (#173) concilie les deux — le run part dans une **console indépendante** (lanceur `<run-id>/lancer.sh`, sortie dans `<run-id>/run.log`) et l'appelant rend la main, ce qui permet de démarrer un run depuis une session sans que le pilote en dépende. Pendant un ticket la console montre **l'avancement du plan** (#240, [docs/10 §11.3](./docs/10-workflow-git.md)) : une **checklist vivante** — chaque ticket avec son état (à venir · en cours · ✓ livré · ✗ échec · ~ sauté) et, une fois jugé, sa PR, sa durée et son coût —, le ticket courant **animé et chronométré** avec **une seule** ligne d'action réécrite sur place (l'attente d'une limite d'usage y est un état, décompté), et un pied qui donne le cumul du run. Le flot d'une ligne par appel d'outil (#176) **ne s'imprime plus par défaut** : il défilait trop vite pour être lu, un nom d'outil sans son résultat n'apprend rien, et il avait chassé de l'écran l'information qu'on y cherche — `--verbeux` (ou `MAESTRO_ORCHESTRATE_VERBEUX=1`) le restitue et **éteint alors la vue**, les deux se disputant l'écran. **Ce bloc tient en place, et rien d'autre n'occupe l'écran** (#284, [docs/10 §11.3](./docs/10-workflow-git.md)) — la vue de #240 était juste, c'est ce qui l'entourait qui la noyait, et deux des trois défauts étaient invisibles à la relecture de `run.log`. Une frame **ne se termine plus par un saut de ligne** : un `\n` écrit sur la rangée du bas fait défiler le tampon, et le bloc y vit — à cinq images par seconde, l'écran paraissait stable pendant que l'historique se remplissait d'une copie du bloc par frame ; le curseur reste donc **sur** la dernière ligne et le repositionnement vaut `hauteur - 1`. Le **curseur est caché** tant que la vue tient l'écran (`vue_ferme` le rend sur toute sortie, Ctrl-C compris) : c'est son va-et-vient, plus que le texte, qui donnait à la console son air agité. Et le **battement** d'une ligne par minute part vers le **journal seul** — à l'écran il n'apprenait rien que le bloc ne dise déjà en plus frais, tout en forçant un redessin « à neuf » qui laissait le bloc précédent derrière lui. Le redessin, enfin, se fait **une fois par seconde** (ou tout de suite sur un changement d'action) : rien de ce que la frame montre ne bouge plus vite, et chaque frame coûte une poignée de forks. Quatre points à connaître avant d'y toucher : la sortie d'un run **n'est pas un terminal** (le lanceur de `--detach` tube vers `tee`, ce qui est déjà toute la raison d'être de `MAESTRO_ORCHESTRATE_COULEUR`), d'où des frames écrites sur un **descripteur dédié** ouvert avant le tube (`exec 4>&1`, passé par `MAESTRO_ORCHESTRATE_CONSOLE_FD`) pendant que stdout garde la trace permanente — en-tête de ticket, verdicts — et, **sans console** (détachement Unix, CI, tests), une vue qui retombe en **plein texte** sans redessin ; le lanceur ouvre **aussi le journal** (`exec 5>>run.log`, `MAESTRO_ORCHESTRATE_TRACE_FD`), sans quoi ni le battement ne pourrait éviter l'écran, ni une ligne devant y être ne pourrait être écrite **par nous** — `tee` est un autre processus, rien ne garantit qu'il écrira avant la frame suivante, et une frame arrivée trop tôt compte ses lignes depuis le mauvais endroit et **dédouble le bloc** (d'où la fonction `trace`, réservée aux endroits où une frame suit de près) ; le **chrono** avance sur l'horloge de `read -t` et non sur l'arrivée d'un événement, ce qui évite tout processus d'affichage à surveiller, mais ce qu'une expiration a déjà lu doit être **recollé** sous peine de couper un objet JSON en deux dans `<iid>.jsonl` ; et la boucle de redessin **ne fait aucun appel réseau** — c'est ce qui la distingue de `status.sh`. **Le bloc rend N tickets en vol, et c'est le pilote qui le dessine** (#290, [docs/10 §11.3](./docs/10-workflow-git.md)) : #289 avait éteint la vue au-delà d'un ticket pour une raison juste — le bloc était dessiné **depuis le sous-shell de la session** et sa hauteur vivait dans un fichier que N sous-shells auraient réécrit l'un sur l'autre, soit un écran corrompu et non une vue dégradée. La réponse n'est pas de partager l'écran entre N écrivains mais de **le retirer à tous sauf un** : le pilote dessine, une session ne fait plus que **publier** son action dans `<iid>.vue`, et ses lignes permanentes passent par une **file** que le pilote vide entre deux frames au lieu de courir avec la frame suivante par `tee`. Trois simplifications en découlent — la hauteur redevient une **variable** (un seul processus la lit et l'écrit), le paramètre `frais` disparaît, et le chrono est **calculé par le pilote** (`P_DEBUT`) donc juste à travers les reprises de session, là où une valeur publiée par une session repartie de zéro le ferait reculer à chaque limite d'usage. Trois pièges à connaître avant d'y toucher : la **hauteur du bloc varie** désormais d'une frame à l'autre (un ticket soldé rend sa ligne d'action), d'où un `ESC[J` final qui efface ce qu'une frame plus haute avait laissé, et un bloc qui **se borne à la fenêtre** en masquant des lignes déjà jouées plutôt que de déborder — déborder ferait défiler, donc dédoubler ; une frame est dessinée **à chaque lancement de ticket** et pas seulement dans la boucle d'attente, qui **ne tourne pas** quand les sessions se soldent aussi vite qu'on les lance (le bloc restait alors vide tout le run — défaut invisible à `--concurrence 1`, révélé au premier essai à trois tickets) ; et la file est **vidée à la sortie** comme dans le trap, une ligne qui y reste n'existant nulle part ailleurs, ni à l'écran ni dans `run.log`. Le compteur du pied, enfin, se compte sur ce qui n'est **ni soldé ni en vol** (`plan − (✓ + ✗ + ~) − en vol`) : `nb_plan - POSITION` désignait la position du **dernier ticket lancé**, qui n'a plus de sens quand les tickets ne se prennent plus dans l'ordre. **Et le repère de ce bloc se recalcule au lieu de se cumuler** (#325, [docs/10 §11.3](./docs/10-workflow-git.md)) : le bloc était repositionné **à partir du curseur**, de `hauteur - 1` rangées vers le haut — un repère **cumulatif**, juste tant que rien n'ajoute une rangée qu'on n'a pas comptée, et faux **pour toujours** dès qu'une l'ajoute. Une seule ligne repliée suffit : la frame suivante remonte trop peu, abandonne la première ligne du bloc derrière elle, et recommence à chaque redessin — sur le run du 2026-08-10 le ticket courant s'affichait **trois fois**, deux décalages jamais rattrapés, chaque copie définitive. Trois changements, du plus profond au plus superficiel : le repère est **ancré sur le bas de la fenêtre** dès que le bloc y touche (`vue_ancre`, `ESC[999B` puis la remontée), déplacement **borné par le terminal** donc position recalculée à neuf à chaque frame — une désynchronisation coûte au plus **une frame fausse** là où elle coûtait une copie par seconde ; la **taille de la console est relue en cours de run** (`vue_mesure`, toutes les deux secondes) au lieu d'être figée à l'ouverture, la figer revenant à parier qu'une fenêtre ne change pas de taille en cinq heures, et un changement déclenche un redessin complet ; la **largeur se mesure en colonnes affichées** (`colonnes`) et non en `${#s}`, qui compte des octets sous une locale C et des caractères sous UTF-8 — le bloc n'avait pas la même largeur d'un poste à l'autre, et la machine qui comptait des octets repliait ses lignes. Deux points à connaître avant d'y toucher : `VUE_ROW`, qui ne répond qu'à « le bloc touche-t-il le bas ? », est une **borne inférieure** assumée — sous-estimer ne coûte que de rester un peu plus longtemps dans le régime relatif, sur-estimer collerait le bloc au bas en laissant un trou sous le journal —, et `vue_mesure` tient une hauteur **inférieure à 10** pour aberrante et lui substitue 40, si bien qu'un test voulant voir le régime ancré sous ce plancher mesure la fenêtre par défaut sans que rien ne le dise. Le flux brut reste intégralement dans `<iid>.jsonl`, `<iid>.json` ne gardant que l'objet `result` final, seul lu pour le coût, le verdict et la limite d'usage. **Deux runs ne cohabitent plus** (#213, [docs/10 §11.9](./docs/10-workflow-git.md)) : un run pose au démarrage la **carte d'identité de son pilote** (`<run-id>/pid` — PID, WINPID, naissance du processus, hôte) et la retire en partant, et tout démarrage — reprise comprise — **tue d'abord les pilotes encore vivants**. Ce qui manquait n'était pas la volonté mais la donnée : `status.sh` *déduisait* l'activité de la fraîcheur des écritures, ce qui suffit à dire qu'un run semble mort, jamais à en tuer un. `scripts/orchestrate/pilote.sh` porte la carte, sa vérification et l'arrêt ; `run.sh` et `status.sh` s'y branchent tous deux. Trois points à connaître avant d'y toucher : **rien n'est tué au jugé** — seulement les PID des cartes et leurs descendants, jamais un `claude.exe` repéré par son nom (la session interactive de l'utilisateur en est un) —, la **naissance** du processus démasque un **PID recyclé** (une carte survit à un SIGKILL, aucun trap ne s'exécute) et une carte invérifiable fait **s'abstenir**, et sous Windows le `taskkill //T //F` sur le WINPID est ce qui emporte la session `claude.exe` native, que `/proc` ne voit pas et que `kill` n'atteint pas. L'arrêt est **sans sommation** (le fichier `STOP` n'est lu qu'entre deux tickets, donc jusqu'à la fin de la session en cours — sans délai par défaut depuis #326, cette attente n'est plus bornée d'avance) mais **borné** : journal intact, run **reprenable**, travail non commité conservé dans le worktree de son ticket. L'ordre compte — on tue **avant** de résoudre `--resume`, sans quoi le run qu'on vient d'interrompre serait écarté de `--reprenables` pour cause d'écritures trop fraîches. `--sans-kill` pour laisser cohabiter (il le dit), `--tuer-les-runs` pour ne faire que ça. `status.sh` (#177) répond à « où en est le run ? » **hors de cette console** — **les** tickets en cours et leur temps écoulé (N depuis #289 : l'écran les rend tous, #290 — n'en montrer qu'un serait pire que rien, les autres tenant un worktree et une session sans que rien ne le dise), commits/fichiers de leur worktree (le signal de progression le plus fiable, `<iid>.json` restant vide jusqu'à la fin), état GitLab, reste du plan, bilan des traités ; `--watch` boucle, `--run-id`/`--list` ciblent un run. Trois corollaires de N : le compteur « à venir » retranche **tous** les tickets en vol, le **silence** se mesure sur le **plus récent** d'entre eux (un run est vivant dès qu'une session écrit encore) et le cache GitLab est indexé **par ticket**, sans quoi le ticket suivant le chasserait à chaque tour de `--watch`. Lecture seule, et l'état « en cours » s'y **lit** dans la carte du pilote quand elle est là (« pilote vivant (pid 1234) », #213) ; sans carte — journal d'avant, ou run tué par SIGKILL — il reste une **déduction** (dernières écritures du run et du worktree), annoncée comme telle. C'est cette lecture, prise **une seule fois**, qui alimente `--reprenables` (TSV lisible par un script) et donc `run.sh --resume [<run-id>]` (#204, [docs/10 §11.8](./docs/10-workflow-git.md)) : **un run coupé se rejoue sur SON plan**, jamais sur un ordre recalculé entre-temps, dans un journal **neuf** (`reprise-de` dit de qui il est la suite — le bilan du run repris n'est jamais écrasé). Les tickets livrés depuis se sautent d'eux-mêmes par leur cycle de vie ; **tous** les tickets **en vol** à la coupure, eux, sont **repris** (#291 — la question est posée par ticket, un run concurrent en ayant N en main) **et la concurrence avec eux** — seule exception au filtre « À faire », étroite (témoin de session sans ligne de bilan dans le run repris) et payée par la même mécanique que la limite d'usage : chaque session Claude est rouverte avec **son** uuid. Un « En cours » que le run repris n'avait pas en main reste sauté : c'est le ticket de quelqu'un d'autre. Le compteur `[n/N]` de la console dit la **position dans le plan**, sautés compris (#230) — compté sur les tickets *tentés*, ce que `--max` continue de faire à dessein, il repartait à `[1/N]` sur le premier ticket d'une reprise. Le **verdict d'un ticket est lu dans la forge** (PR ouverte *et* cycle de vie « En revue »), jamais dans la prose de la session. **Deux choses ne sont pas des limites d'usage** (#203) : une session sortie en **0** — elle est allée au bout de son tour, rien ne l'a coupée, la détection ne se consulte donc que sur un **échec** — et la **télémétrie** que le CLI place en tête de *chaque* flux (`{"type":"rate_limit_event","rate_limit_info":{"status":"allowed","resetsAt":…}}`), qui ne fait que rapporter la fenêtre de 5 h en cours ; grepée avec le reste du `.jsonl` depuis #176, elle faisait matcher `rate limited` **et** livrait son `resetsAt` comme heure d'attente — un run est parti dormir jusqu'au reset **après** avoir livré son ticket, dont le verdict GitLab n'a jamais été lu. Ces lignes sont donc écartées avant toute recherche, sauf vrai refus (`"status":"rejected"` — à ne pas confondre avec `"overageStatus":"rejected"`, autre clé du même objet). **Une session qui croit faire une pause termine le ticket** (#178) : en mode `-p` la fin du tour est la fin du processus, et « j'attends la fin du run de couverture » sort en code 0, indiscernable d'un succès — le prompt interdit donc d'attendre un **résultat** autant qu'une validation (avant-plan, ou trancher sans lui, ou `ORCHESTRATE: ECHEC`) et couvre la reprise du **travail non commité** ; côté boucle, l'échec regarde le worktree et distingue « session terminée sans clôture, N fichier(s) non commité(s) » (rattrapable) de « sans rien produire (worktree propre) ». Journal dans `.maestro/orchestrate/<run-id>/`, arrêt d'urgence par `.maestro/orchestrate/STOP`. Ce journal **ne s'accumule plus** (#198) : `journal.sh gc`, déclenché au démarrage de chaque run, ne garde que les **N derniers runs** (défaut 10), ramasse les répertoires vides des sorties précoces et **gzippe le `<iid>.jsonl`** — le flux brut de #176, seul poste qui grossit vraiment — dès le verdict rendu, jamais avant (la détection de limite d'usage le relit entier à chaque tentative). Il n'ôte **jamais** le run courant ni un run qui écrit encore (le ménage se contente de la dernière écriture — il n'a pas besoin de la carte du pilote pour être prudent), il est **best-effort** (son échec ne fait pas échouer un run), et `gc --check` dit ce qui partirait sans rien écrire. **Le résultat d'une session se lit désormais à l'œil nu** (#180) : `<iid>.json` reste brut — c'est lui que grepent le verdict, le coût et la limite d'usage — mais un `<iid>.resultat.txt` est écrit **à côté** à chaque verdict (verdict GitLab, état de session, durée, coût, refus de permission comptés par outil puis détaillés, message final désescapé), et une session morte sans rendre la main le dit au lieu de laisser une vue vide. Lecture faite en `awk`, sans `jq` ni Python ; `run.sh --resultat <fichier.json>` rejoue la même vue sur un journal antérieur. Au passage le **coût est arrondi** à deux décimales (console et `resume.tsv` — `LC_ALL=C`, la colonne étant relue en awk) et les **runs sans suite ne s'accumulent plus** : un plan vide ou un `queue.sh` en échec renonce à son répertoire, sauf s'il porte autre chose que le plan. Ses invariants sont testés par [`tests/test_orchestrate.py`](./tests/test_orchestrate.py) (#172 puis #175, #178, #179, #180, #203, #204, #213, #217, #230, #235, #240, #284, #286, #325, #326 et le chantier concurrent #288-#291, couvert par #292 — dépôt jetable, ni réseau ni quota ni écriture GitLab ; seuls les tests de l'arrêt lancent de **vrais** processus, qu'ils tuent pour de bon — vérifier qu'un arrêt arrête ne se simule pas, et depuis #291 c'est un pilote, ses N sous-shells et un petit-fils par sous-shell dont on observe le **battement**, un `kill -0` répondant encore « vivant » à un processus tué mais pas encore ramassé). Une règle à connaître avant d'ajouter un test de concurrence (#292) : **ce qui doit être simultané l'est par une barrière, jamais par un `sleep`** — chaque session bouchon signale son arrivée puis attend les autres, et les sessions tiennent elles-mêmes le **pic de simultanéité**, seule mesure qui distingue « jamais ensemble » de « ensemble mais trop vite pour être vu » ; sans elle, « deux tickets en vol » est une course que la charge de la machine tranche, et le test dit tantôt le code, tantôt l'ordonnancement du système. **Et la mesure obéit à la même règle que ce qu'elle mesure** (#313, [docs/10 §11.10](./docs/10-workflow-git.md)) : le pic était tenu par un compteur **partagé**, lu puis réécrit en deux commandes, donc perdant une incrémentation dès que deux sessions arrivaient ensemble — c'est-à-dire exactement ce que la barrière rend probable. Chaque session écrit désormais **son** relevé dans **son** fichier (aucun fichier à deux écrivains, maximum pris après coup par `_pic`), et une barrière qui renonce faute d'être levée à temps le **dit** au lieu de laisser un pic trop bas passer pour un verdict. Le défaut ne coûtait pas ce test mais **n'importe quelle PR** touchant `scripts/orchestrate/**`, le filet local et le pipeline jouant en parallèle. **Après un run, `bash scripts/orchestrate/journal.sh refus [<run-id>|--tous]`** classe les refus par **famille** (#307, ci-dessus) puis les agrège par outil et par commande (chaque maillon d'une chaîne compté pour lui-même, provenance et exemple) : c'est ce qui rend tenable le principe de [§11.7](./docs/10-workflow-git.md) — l'`allow` s'instruit **à partir des refus observés** —, et le résumé de fin de run rappelle la commande.

Ces commandes utilisent le CLI `gh` (authentifié via `gh auth login`) pour lire/écrire les issues et Pull Requests GitHub. Si `gh auth status` échoue, arrêter et demander à l'utilisateur de s'authentifier plutôt que de continuer sans. Le CLI `glab` n'est plus un prérequis du dépôt (#344) : il ne sert qu'à relire l'**archive** GitLab, par les seules primitives de `scripts/migration/gitlab-lecture.sh` ([docs/27 §11](./docs/27-decision-gitlab-vers-github.md)).

Elles s'appuient sur le helper bash `scripts/gitlab/lib.sh`, qui factorise les appels `gh` (résolution du work-item, pose du **cycle de vie par nom** via `set-workflow` — projet, champ Status et option résolus par leur nom, aucun ID en dur —, **dates & time tracking** via `start-dates`/`log-time`, slug, préfixe de branche, listing du backlog, **milestones** via `milestones`/`milestone-issues`, **sous-tickets** via `issue-link`/`parent-of`/`subtickets`/`startables`, **retard sur `origin/main`** via `behind-main`, **mise à jour de `main`** via `sync-main`). Sourçable (`. scripts/gitlab/lib.sh`) ou en sous-commandes (`bash scripts/gitlab/lib.sh set-workflow <iid> "En cours"`).

**Descriptions GitLab : toujours passer par les helpers** `get-description`/`set-description` (ticket) et `get-mr-description`/`set-mr-description` (PR) pour tout aller-retour lecture→réécriture — cocher la checklist d'un parent, mettre à jour celle d'une PR — **et `create-mr`/`issue-note` à la création** (#233), les pendants qui manquaient : `bash scripts/gitlab/lib.sh create-mr <iid> <fichier>` ouvre la PR en Draft vers `main` (titre lu dans le ticket via `issue-title`, description lue dans le fichier, idempotent — une PR ouverte est mise à jour au lieu d'échouer) et `issue-note <iid> <fichier>` poste un commentaire. **Le texte long voyage par un FICHIER, jamais sur la ligne de commande** : la couche permissions découpe un appel sur ses **sauts de ligne** et ne matche aucune **substitution `$(…)`**, si bien qu'un `gh pr create --body` multi-ligne — et son repli `--body "$(cat …)"` — sont refusés alors même que `gh pr create` est autorisé. C'était la cause n°1 des refus des sessions autonomes, sur la **dernière action du ticket** (10 refus, 8 sessions sur 16 — [docs/10 §11.7](./docs/10-workflow-git.md)). Écris le fichier avec l'outil `Write`, puis passe son **chemin**. Ne **jamais** improviser un `gh issue view --json body | python` : sous Windows, `sys.stdin` décode en cp1252 et repousse du mojibake (« Ã© » au lieu de « é ») dans la description — c'est arrivé sur un parent (#141). Le piège classique est d'écrire `PYTHONIOENCODING=utf-8 gh … | python`, où la variable s'applique à `gh` et **n'est pas propagée** au python du pipeline ; les helpers restent en shell pur, byte-transparent. Vérifier une correction d'encodage se fait **par octets**, jamais à l'affichage (un terminal cp1252 réaffiche le mojibake de façon plausible).

Bilan de santé (lecture seule) : `bash scripts/gitlab/doctor.sh` vérifie auth et labels, et **détecte les dérives** cycle de vie↔PR (ticket « En revue » sans PR, ticket fermé au cycle de vie encore actif, **ticket sans état** — la dérive propre au dispositif par champ, que rien d'autre n'attrape : elle est détectée, mais son message parle encore de labels et ne distingue pas encore ses deux causes, « hors du projet » et « item au Status vide » (#363) —, branche locale mergée à nettoyer, réglages de merge « pipeline vert requis » et « suppression de la branche source au merge » retombés).

Présentations de milestone (`/milestone-presentation`) : `scripts/presentation/` porte les trois étapes — `captures.sh` (captures de la Control Tower : monte une stack **de production** sur ses propres ports 8010/3010, `playwright-core` + Edge installés dans un dossier temporaire, jamais dans le dépôt), `captures.mjs` (le pilotage du navigateur) et `build.py` (JSON → HTML autonome, gabarit et CSS inclus). Les captures **ne passent pas par le serveur de dev** : en mode dev, la WebSocket de rechargement à chaud de Next échoue dans le navigateur headless et bloque l'hydratation — toutes les pages sortiraient en « Reconnexion… / Chargement de l'état… ».

Hooks git : posés par `scripts/setup.sh` (ou, seul, `bash scripts/git/install-hooks.sh` — une fois par clone). Le hook `commit-msg` valide la convention de commit (Conventional Commits + `Refs`/`Closes #<iid>`). Bypass ponctuel : `git commit --no-verify`.

**Un worktree par ticket** ([docs/10 §9](./docs/10-workflow-git.md)) — un clone n'a qu'un répertoire de travail, donc deux sessions Claude Code ouvertes dessus se marchent dessus. Depuis #181 c'est **`/ticket-start` qui monte le worktree** (§9.1) : le geste manuel ci-dessous reste disponible mais n'est plus la voie normale. `bash scripts/git/worktree.sh <iid>` monte un second répertoire de travail sur le **même** dépôt : branche créée depuis `origin/main`, `.env` recopié, `.venv`/`.tools` partagés par lien (`apps/web/node_modules` est installé sur place — Turbopack refuse un `node_modules` lié), **atelier de session `.maestro/session/`** (#307, [§11.7](./docs/10-workflow-git.md) — l'endroit désigné où une session écrit ses fichiers de travail, seul atteignable en chemin relatif) et surtout **ports Control Tower et profil de navigateur dédiés** (sans quoi les sessions s'arrêtent mutuellement la stack et se disputent le verrou du profil Chrome). `list`/`remove <iid>` pour le reste du cycle — **retirer un worktree ne supprime jamais sa branche** (`create`/`remove`/`gc` n'y touchent pas ; la seule suppression du script est la purge que `ensure` délègue à `cleanup-merged`, #305). Dans un worktree, `main` est emprunté par le clone principal : ne jamais y faire `git checkout main` — `lib.sh start-branch <branche>` (appelé par `/ticket-start`) s'en charge correctement des deux côtés. **La fin de vie, elle, ne demande aucun geste** (#197, [§9.2](./docs/10-workflow-git.md)) : `worktree.sh gc` retire les worktrees dont la forge confirme la **PR mergée ou le ticket fermé** — pendant exact de `cleanup-merged` sur les branches, câblé dans `ensure` (donc `/ticket-start`), dans `/branch-cleanup` **avant** la purge des branches (`git branch -D` refuse une branche empruntée par un worktree) et au démarrage d'un run `/orchestrate`. Il ne déduit rien du nom de la branche, ne touche jamais au worktree de la session courante, et **signale au lieu de supprimer** un worktree porteur de travail non sauvegardé — fichiers non commités ou commits absents du serveur, mesurés contre le **sha de merge** parce qu'un squash rend `origin/main..HEAD` inutilisable. **Sur ce même verdict il pose le cycle de vie « Terminé »** (#275, [§9.2](./docs/10-workflow-git.md)) : le merge ferme le ticket mais ne touche à aucun label, si bien qu'un ticket livré s'affichait « En revue » jusqu'au prochain `/branch-cleanup` manuel — dérive que `doctor.sh` diagnostiquait sans jamais la réparer (22 tickets au moment du câblage). La greffe est **ici** et pas dans `ensure` parce que « soldé » *est* la question de la réconciliation : aucune lecture de découverte en plus, aucune cinquième étape au démarrage, et les trois points de passage de `gc` en héritent d'un coup. Trois choix à ne pas défaire : la pose a lieu **avant** le garde-fou du travail non sauvegardé et **indépendamment du retrait** (le cycle de vie suit GitLab, pas la propreté d'un répertoire local — sans quoi un fichier oublié laisserait son ticket « En revue » pour toujours) ; elle est **best-effort et muette en échec**, au même titre que `sync-main` ; et elle **n'écrase jamais « Abandonné »/« Doublon »**, fermés eux aussi donc « soldés » eux aussi — un filtre sans lequel ramasser le worktree d'un ticket abandonné le déclarerait « Terminé », sans retour possible. Le verbe est utilisable seul (`bash scripts/gitlab/lib.sh reconcile-workflow [--check] [<iid>…]` — sans iid il balaie tout le backlog fermé, et c'est ce que `doctor.sh` propose désormais quand il détecte la dérive) ; `MAESTRO_WORKFLOW_POSE=0` l'éteint. La couverture est celle des **worktrees vus par cette machine** — le board restait faux **au repos**, limite levée par #377 (ci-dessus), qui pose l'état à la fermeture du ticket sans dépendre d'aucun poste ; ce qui reste ici est le **filet** : ce qu'un secret absent, un jeton périmé ou un incident GitHub aurait laissé passer. Deux barrières protègent « Abandonné »/« Doublon », et depuis #388 **chacune arrête ce que l'autre ne voit pas** : `/ticket-abandon` ferme par `gh issue close <iid> --reason "not planned"` (ses deux variantes, doublon compris), donc la raison de fermeture (liste blanche sur `completed`) l'écarte **avant toute lecture** ; le filtre d'**état** de `reconcile-workflow` reste le filet du geste **manuel** — un ticket déjà « Abandonné » refermé « as completed » depuis l'interface web —, et il tient parce que la commande pose l'état avant de fermer. Avant #388 la commande fermait **nu**, donc en « completed » comme n'importe quel merge : la première barrière laissait entrer tout abandon et la seconde était la seule couche active, ce qui faisait de la « défense en profondeur » une défense à une couche. **La branche `main` locale, enfin, ne prend plus de retard** (#205, [§9.3](./docs/10-workflow-git.md)) : `lib.sh sync-main` l'avance sur `origin/main` en **fast-forward seulement**, câblé dans `ensure` (donc tout `/ticket-start`, manuel comme autonome), dans `/branch-cleanup` et **au démarrage d'un run `/orchestrate`** (#283 — pas un doublon du premier : un run est ce qui fait vieillir `main` le plus vite, puisqu'il ouvre N PR destinées à être mergées, et la mise à jour par `ensure` a lieu *dans* une session, donc pas du tout quand le run part sur un plan vide, saute tous ses tickets ou échoue avant le premier ; elle passe **avant** le ramassage des worktrees, dont la mesure du travail non sauvegardé s'appuie sur l'`origin/main` que ce `fetch` vient de rafraîchir, et un `--dry-run` ne la joue pas). Le point à comprendre avant d'y toucher : ce qui était périmé, c'est `refs/heads/main` du clone principal — plus personne n'y repassait depuis #181 — et **jamais `origin/main`**, rafraîchi partout et seule base des worktrees, donc le code produit n'a jamais été en cause. Aucun événement local n'existe pour s'y accrocher (le merge a lieu sur GitLab, `post-merge` ne réagit qu'à un merge *local*), d'où le câblage aux points de passage obligés. Il **s'abstient en le disant** — `main` divergent, répertoire porteur sale — plutôt que de forcer, et son code de retour n'est jamais fatal : une abstention n'empêche ni un ticket de démarrer ni un run de continuer. **Les dépendances ajoutées au dépôt suivent de la même façon** (#216, [§9.4](./docs/10-workflow-git.md)) : `ensure` demande la dérive à `bash scripts/setup.sh --derive` (TSV « `<étape><TAB><raison>` », 0 = à jour / 3 = dérive, sans réseau ni écriture) et la répare en appelant `setup.sh --only <étapes>` — **jamais un `pip`/`npm` réimplémenté ailleurs**. Trois points à connaître avant d'y toucher : aucun hook git ne pouvait porter ça (même raison qu'en §9.3 — `update-ref` ne déclenche rien), c'est le **clone principal** qu'on remet à niveau parce que `.venv`/`.tools` y vivent et que l'installation éditable de `maestro` doit continuer d'y pointer (#194) — d'où une dérive du venv évaluée là-bas même appelée depuis un worktree, dont tous les fichiers datent de sa création —, et **ça ne bloque jamais un démarrage** (`MAESTRO_MAJ_DEPENDANCES=0` pour l'éteindre). Le filet CI local, lui, **signale sans installer** ([§8.4](./docs/10-workflow-git.md)) : bloc « Dépendances en retard » avant son verdict, qui généralise le message jusque-là limité à `pytest-xdist`. **Et les branches mergées repartent, elles aussi, d'office** (#305, [§9.5](./docs/10-workflow-git.md)) — cinquième membre de la famille, mais le seul antérieur aux autres : `cleanup-merged` purge les branches locales mergées depuis #23, c'est son **déclencheur** qui avait cassé. Il vivait dans `lib.sh start-branch`, sur la voie « clone principal + branche à créer », que #181 a rendue injoignable : `/ticket-start` appelle `ensure` **d'abord** et relocalise la session, si bien que `start-branch` sort toujours par « déjà sur la branche » ou par sa voie worktree — 35 branches mergées accumulées au constat du 2026-08-07, la plus ancienne remontant à #220. Exactement la panne de #205, sur un autre objet, à ceci près qu'un `main` en retard se lit dans l'IDE là où une branche morte de plus ne se remarque pas. La purge est donc câblée dans `ensure`, **après** le ramassage des worktrees (`git branch -D` refuse une branche empruntée, donc la branche d'un ticket soldé n'est supprimable qu'une fois son worktree parti) et en mode `--auto` (muet s'il n'y a ni suppression ni refus, comme `gc --auto`). Trois choix à ne pas défaire : elle a été **retirée de `start-branch`** au lieu d'y être laissée en double — un second déclencheur inatteignable est précisément ce qui a rendu la panne invisible, le code étant là et la doc le décrivant ; le helper **vise le clone principal** d'où qu'on l'appelle, comme `sync-main` et `gc` — les refs sont partagées, donc la liste serait la même de partout, mais l'arbre que regarde son garde-fou est alors celui du clone principal, normalement propre, et non celui d'un worktree en plein travail qui la ferait s'abstenir en silence à chaque reprise ; et une branche mergée que `git branch -D` **refuse** est désormais comptée à part et **nommée** avec le worktree qui la retient, là où l'échec n'incrémentait aucun des deux compteurs et sortait la branche du compte rendu sans un mot (3 sur 41 à la purge de rattrapage, pour un bilan qui annonçait moins de branches qu'il n'en avait examinées). `MAESTRO_PURGE_BRANCHES=0` l'éteint ; `/branch-cleanup` reste le geste à la demande. **Le sixième membre, enfin, réconcilie non pas un répertoire mais un ticket** (#327, [§9.6](./docs/10-workflow-git.md)) : un ticket entre en « En cours » **et assigné** à `/ticket-start` et n'en sort que par une clôture ou un abandon — la **troisième sortie est l'absence de sortie**, et « En cours » + assigné est exactement ce que `queue.sh` écarte, si bien que **la règle qui protège le travail vivant cache définitivement le travail mort** (constat du 2026-08-11 : #316, 2047 lignes commitées jamais poussées, dont la chute avait en plus sauté les 7 lots suivants de son parent ; #325, 396 lignes non commitées). Le renversement fait tout le travail : ne pas demander « ce run a-t-il échoué ? » mais **« quelqu'un s'occupe-t-il encore de ce ticket ? »** — question posée au **worktree**, donc valable pour les trois modes de mort, dont **deux échappent par construction à `--resume`** (un run soldé en échec porte une ligne de bilan, que `reprend_en_vol` exclut, et son run est « terminé » donc pas même reprenable ; une session interactive laissée en plan n'a ni journal ni témoin ; seul le pilote tué est rattrapable, et seulement en reprenant *ce run-là*). Deux verbes, et l'asymétrie entre eux est le sujet : `lib.sh reconcile-en-cours` **signale** — lecture seule intégrale, trois verdicts (**vivant** par la carte du pilote #213 quand elle est là, sinon par la fraîcheur du worktree ; **orphelin** = worktree présent ici et muet depuis plus de 6 h ; **hors de portée** = aucun worktree ici, car ne rien savoir n'autorise rien) — et `lib.sh reprendre-en-cours <iid>` **rend prenable**. « Prenable » est une **conjonction** parce que le filtre de `queue.sh` en est une (« À faire » **ET** libre), d'où une **seule mutation** qui pose le cycle de vie et vide la liste des assignés : deux appels laisseraient un intervalle où le ticket est dans un état que personne n'a voulu. Le verdict n'y est **jamais redéduit**, il est demandé au premier verbe — deux formules qui divergeraient se remarqueraient trop tard —, et `--force` lève le garde-fou **jamais en silence**. Quatre points à connaître avant d'y toucher : le **seuil de 6 h** (`MAESTRO_ORPHELIN_SEUIL`) est généreux parce qu'une session qui épuise la limite d'usage dort sans rien écrire et que `run.sh` l'attend jusqu'à 5 h 30 — plus court, il déclarerait abandonné un ticket dont la session attend légitimement ; la **carte du pilote ne prouve que la vie** (elle survit à un `taskkill //F`, aucun trap ne s'exécutant), donc une carte morte ne sauve pas le ticket ; la reprise **n'écrit que dans GitLab** — worktree, branche, commits non poussés et fichiers non commités **intacts**, `worktree.sh ensure` les retrouve au démarrage suivant, et c'est exactement ce qu'on veut des 2047 lignes de #316 : un verbe qui « nettoierait » au passage détruirait ce qu'il est censé sauver ; et le **plafond de 2 reprises par ticket** (`MAESTRO_REPRISES_MAX`, `--force` pour insister) vit dans `.maestro/orchestrate/reprises.tsv`, **à côté** des répertoires de run et non dedans — une reprise est une propriété du ticket (celle de #325 n'a jamais eu de run), et un compteur que le ménage du journal remettrait à zéro tous les dix runs est un compteur qui n'existe pas. Le signalement est greffé sur **`gc`** et non sur `ensure`, pour la raison exacte qui y a fait greffer la pose du cycle de vie : les **trois** points de passage en héritent d'un coup (`/ticket-start`, `/branch-cleanup`, démarrage d'un run), là où un câblage par point de passage en ferait trois à garder d'accord — et il est **muet quand il n'y a rien**, comme `gc --auto`. Il se voit aussi dans `doctor.sh` (dérive 4d, la seule des quatre qui demande de regarder un disque plutôt que GitLab), dans `queue.sh --orphelins` (ceux du milestone visé, avec run d'origine et plafond, **à côté** du plan et jamais dedans) et dans `/orchestrate`, qui les propose au feu vert — un « oui » explicite, jamais un contournement automatique du filtre : « orphelin » est une **déduction**, et reprendre le ticket d'une session vivante le lui retire, là où rater un orphelin ne coûte qu'un tour de boucle. Portée annoncée, comme `gc` et `reconcile-workflow` : les **worktrees de cette machine** — le board reste faux au repos, ce n'est pas une régression mais ça se dit. `MAESTRO_EN_COURS_SIGNAL=0` éteint le signalement. Couvert par [`tests/test_collaboration.py`](./tests/test_collaboration.py) (les trois modes de mort joués jusqu'à la reprise, l'empreinte du worktree identique avant/après, le plafond qui survit au ménage du journal et ne se contourne pas depuis un worktree, la dérive `doctor.sh`), [`tests/test_worktree.py`](./tests/test_worktree.py) et [`tests/test_orchestrate.py`](./tests/test_orchestrate.py). **Le septième verbe ne répare rien, il rend adressable** (#385, [§9.7](./docs/10-workflow-git.md)) : Claude Code range le transcript d'une session sous le **répertoire courant**, et son sélecteur `/resume` ne montre que celui d'où on l'appelle — donc l'historique d'un ticket, produit dans son worktree, est invisible depuis le clone principal, puis `gc` retire le worktree et on ne peut même plus y revenir en `cd` (constat du 2026-08-19 : **157 transcripts, 183 Mo, 134 répertoires de projet pour 13 worktrees encore là**). `bash scripts/git/worktree.sh sessions [<iid>|--tous]` rend date, nom d'onglet, titre, identifiant et la commande de reprise — `claude --resume <id>`, qui court-circuite le sélecteur et donc son cloisonnement. Trois choix à ne pas défaire : l'adressage se **dérive** (l'encodage remplace `:`, `\`, `/` et l'espace par `-`, un motif sur l'iid suffit) et n'est **jamais indexé au ramassage** — un index n'aurait couvert que les ramassages postérieurs à sa pose, laissant dehors les 121 worktrees déjà partis ; la base vient de `create` et non d'un `maestro-worktrees` figé, `MAESTRO_WORKTREE_DIR` déplaçant l'encodage donc ce qu'il faut chercher ; et le motif **ignore la casse**, Claude Code encodant le chemin tel qu'il lui a été donné (`e--` pour le clone principal, `E--` pour ses worktrees sur la machine de référence). `gc` **nomme les sessions avant de retirer** — le retrait ne les efface pas, il coupe le seul chemin qui les montrait, et c'est l'instant où l'information quitte l'écran. **Et depuis #397, le geste le plus court répond à la question la plus fréquente** ([§9.7](./docs/10-workflow-git.md)) : `sessions` **sans argument** rend les **10 dernières sessions du répertoire courant**, clone principal compris — la question ne se pose pas par iid mais **là où l'on est**, en rouvrant VS Code sur un onglet vide (191 transcripts sous le clone principal, aucun moyen de nommer celui d'hier) ; l'inventaire de #385 n'a pas disparu, il se demande (`--tous`). Le **nom d'onglet** vient du registre `<config>/sessions/<PID>.json`, seule source qui le porte — un titre est posé en cours de route, parfois jamais, alors que le nom est celui qu'on avait sous les yeux ; une session **reprise** gardant son identifiant sous un nouveau PID, c'est la fiche **la plus récente** qui donne le nom. La liste est **bornée à 10 et le dit** (`--limite 0` rend tout) : tout rendre reperdait la conversation d'hier dans 390 lignes, en rendre 10 en silence ferait passer une troncature pour un inventaire. Et « ce dossier » veut dire ce dossier — les sessions de worktrees sont **annoncées en pied**, jamais mêlées à la liste, où elles proposeraient une reprise dans un répertoire qui n'est pas celui de la session. ⚠ **La prémisse de #385 était fausse** et c'est ce que ce ticket corrige : le registre n'est pas « périmé dès que les processus meurent » — indexé par PID, oui, mais il porte le `cwd`, le `sessionId` et le nom, et il **survit** (36 fiches sur le poste de référence, en majorité de processus morts) ; le PID ne périme qu'une question qu'on ne pose pas ici, « cette session tourne-t-elle encore ? ». Reste **hors de portée** : que l'onglet se rouvre **tout seul** sur sa conversation — vérifié le 2026-08-20 sur l'extension 2.1.237, sa clé `sessionGroups:<hash>` est absente du `state.vscdb` (globalStorage et les 15 workspaceStorage) et son « Reopen Closed Session » travaille sur une pile en mémoire. On outille la reprise sans la rendre automatique ; `claude -n "<nom>"` aide en complément.

Traçabilité des demandes (hook `UserPromptSubmit`) : **chaque demande de travail se consigne dans GitLab, sans confirmation.** Si elle relève du **ticket en cours ou d'un ticket existant** → le **mettre à jour** (commentaire `lib.sh issue-note <iid> <fichier>`, description via `set-description` si le périmètre change) ; sinon → **créer un ticket** via `/ticket-create` (labels `type::`/`agent::`/`prio::`, milestone courant). **Exceptions** : les commandes `/ticket-*` elles-mêmes (déjà tracées) et les échanges purement conversationnels sans travail demandé. Le hook est **versionné** ([`.claude/settings.json`](./.claude/settings.json) déclare le hook, [`.claude/hooks/maestro-demande-ticket.json`](./.claude/hooks/maestro-demande-ticket.json) porte le rappel via `$CLAUDE_PROJECT_DIR` — fonctionne sur tout clone) ; désactivation locale via `.claude/settings.local.json`. Détail : [docs/10 §7.2](./docs/10-workflow-git.md).

Permissions (allowlist) : [`.claude/settings.json`](./.claude/settings.json) (versionné, partagé) **autorise sans prompt** les commandes git/`gh` non destructrices du workflow (`git status`/`diff`/`add`/`commit`/`push`/`pull`, `gh issue` view/list/create/edit/comment, `gh pr` view/list/create/edit/diff/ready, `gh run` list/view/rerun, `gh workflow` list/view/run, `gh api user`/`graphql`, `bash scripts/gitlab/lib.sh`…) ainsi que les outils des serveurs MCP du dépôt (`mcp__chrome-maestro`, `mcp__figma-officiel`), pour que `/ticket-ship` et les autres commandes s'enchaînent sans blocage. L'**étape worktree de `/ticket-start`** en fait partie (#199) : le tool **`EnterWorktree`** et les verbes **non destructifs** de `worktree.sh` (`ensure`, `list`, `gc`). Deux points à connaître avant d'y toucher — `EnterWorktree` s'écrit **nu, sans spécificateur** (comme `Skill`, il ne déclare pas de `ruleContentField`, donc une règle paramétrée ne matcherait jamais rien — #179), et le `allowed-tools:` du frontmatter d'une commande **ne vaut pas permission** (c'est la couche permissions qui tranche, `/ticket-start` le déclarait déjà sans que la question cesse d'être posée). Rien de tout cela n'est un élargissement : monter un répertoire de travail et s'y placer n'écrit pas côté GitLab, ne supprime aucune branche et ne force-pushe rien — et `worktree.sh remove` reste **hors** de l'`allow`, son `--force` pouvant détruire des changements non commités. Les actions destructrices restent barrées côté permissions, en écho aux garde-fous : **`deny`** sur les force-push (`git push --force`/`-f`/`--force-with-lease`), sur `gh pr merge`/`pr close` et sur `gh run delete` ; **`ask`** (confirmation explicite, jamais silencieux) sur `git commit --no-verify`, `git reset --hard`, `git clean`, `gh issue close`, et sur `mcp__chrome-maestro__browser_run_code_unsafe` (exécution de JS arbitraire dans la page). Les surcharges personnelles vont dans `.claude/settings.local.json` (non versionné) : chemins machine, bloc `env` (dont `MAESTRO_CHROME_PROFILE`, `GH_CONFIG_DIR`) et approbation des serveurs de `.mcp.json` (`enabledMcpjsonServers`). Les clés attendues sont documentées par le gabarit versionné [`.claude/settings.local.example.json`](./.claude/settings.local.example.json) — **valeurs neutres, aucun secret**, et **référence à lire plutôt que fichier à recopier** : le vrai `settings.local.json` est écrit par l'étape `mcp` de `setup.sh`, qui renvoie vers le gabarit en `--check`. C'est ce bloc `env` qui donne aussi à un projet **son propre compte GitHub** : `GH_CONFIG_DIR` isole la configuration de `gh` — donc son `hosts.yml`, donc son compte actif —, là où `gh auth switch` bascule toute la machine d'un coup, y compris un run `/orchestrate --detach` qui n'a rien demandé. Recette (config dir, `gh auth login` par dossier) et **deux limites** qui n'en relèvent pas — l'**auteur des commits** (`git config --local user.name`/`user.email`) et le **credential helper de `git push`**, global et résolu sur le config dir ambiant, donc faux depuis un terminal nu — en [docs/10 §7.4](./docs/10-workflow-git.md) ; ne pas la recopier ici.

Serveurs MCP de Claude Code : [`.mcp.json`](./.mcp.json) (versionné) déclare `chrome-maestro` (pilotage du navigateur via `@playwright/mcp`) et `figma-officiel` — un clone les reprend sans réinstallation, il ne reste qu'à les **approuver** au premier lancement. Ne **jamais** y figer de chemin machine ni de secret : le profil du navigateur passe par `${MAESTRO_CHROME_PROFILE}` (défaut `.maestro/chrome-profile`, gitignoré), posé par personne dans le bloc `env` de `.claude/settings.local.json` ; Figma s'authentifie en OAuth par utilisateur. **Fermer la fenêtre du navigateur dès que la séquence est terminée** (`browser_close`), à la fin de *chaque* séquence et pas seulement en fin de session : Chrome n'accepte **qu'un seul consommateur à la fois** sur un `--user-data-dir` (verrou ProcessSingleton), donc une fenêtre laissée ouverte bloque tout autre outil pointant le même profil — et si une étape suivante en a besoin, elle rouvrira. Le skill `verify` et `scripts/presentation/captures.sh` ne sont pas concernés : ils lancent Edge sans profil persistant. À ne pas confondre avec [`core/mcp/<agent>.json`](./core/mcp/README.md), qui équipe les **agents Maestro** (le produit) et non l'outil de développement — voir [docs/21](./docs/21-configuration-mcp.md) et la section « Mise en route côté Claude Code » du [README](./README.md).

**Aucun runner à tenir allumé** ([docs/10 §8.1](./docs/10-workflow-git.md)) — la CI tourne sur les exécutants **hébergés** de GitHub. C'est le gain chiffré du chantier de migration (#344) : **1 146 lignes** d'outillage retirées (`setup-runner.sh`, `ensure-runner.sh`, `clean-runner-containers.sh`), et surtout la contrainte qui les avait fait naître — les runners partagés GitLab étant coupés (#135) et un pipeline vert conditionnant le merge, **une machine de l'équipe devait rester allumée en permanence**, et son extinction bloquait tout le monde. Si un pipeline reste `pending`, ce n'est donc plus un runner à réveiller : Docker n'entre plus dans la CI, et ne sert plus qu'aux bases locales optionnelles (`infra/`).

**Migration GitLab → GitHub : `scripts/migration/`** ([docs/27 §11-§12](./docs/27-decision-gitlab-vers-github.md), parent #335) — `export-gitlab.sh` et `import-github.sh` sont les **seuls scripts du dépôt à parler encore à GitLab**, par les primitives de `gitlab-lecture.sh` (`glab` n'est plus un prérequis : qui rejoue l'un des deux l'installe à la main). Leur travail **ne se rejoue pas** — GitHub numérote séquentiellement et ne laisse pas choisir un numéro d'issue —, d'où une couverture (#345, [`tests/test_migration.py`](./tests/test_migration.py)) portée sur les **invariants non rejouables** : l'ordre (l'objet créé pour l'iid N porte le numéro N, sans quoi les 270 `Refs #<n>` de l'historique deviennent *faux* et non morts), les **trous** comblés par un bouche-trou fermé, les **octets** (aucune étape ne décode puis ré-encode — c'est l'aller-retour du mojibake de #141, vérifié **sur les octets** et jamais à l'affichage), l'**idempotence** du ré-assemblage et la **reprise** sur journal, commentaire par commentaire. Le harnais est un **dépôt GitHub simulé** — un `gh` factice qui *tient une séquence* —, et non celui de [`tests/harnais_forge.py`](./tests/harnais_forge.py), sans mémoire par construction : une séquence ne s'observe que sur un dépôt qui en tient une. Écrire ces tests a sorti **quatre défauts silencieux** de l'import ([docs/27 §12.5](./docs/27-decision-gitlab-vers-github.md)), dont deux perdaient de la donnée : `	` dans un `grep -E` ne désigne pas une tabulation (aucun ticket abandonné n'a jamais reçu `not_planned`), et `IFS=$'	' read` **fusionne** deux tabulations consécutives — un champ vide au milieu d'une ligne décale tous les suivants, donc un milestone sans échéance prenait sa description pour titre et un commentaire sans auteur était sauté. À connaître avant d'écrire une boucle `while IFS=$'	' read` : le champ optionnel voyage avec un **marqueur**, comme dans le journal d'import.

Provisionnement d'un nouveau dépôt : **deux scripts, et l'ordre compte**. `bash scripts/gitlab/bootstrap.sh` pose les **labels de catégorisation** (`type::`/`agent::`/`prio::`) — il ne provisionne plus le cycle de vie depuis #365, les six `workflow::*` ayant été retirés ; `bash scripts/github/bootstrap-project.sh` monte le **projet Projects v2 et son champ Status aux six valeurs**, sans lequel aucun ticket ne peut porter d'état et `/ticket-start` ne démarre rien. Ce qu'ils ne font pas est nommé dans leur sortie plutôt qu'appliqué à moitié : la **protection de branche** a son propre script ([`scripts/github/protect-main.sh`](./scripts/github/protect-main.sh), écrit mais non joué — [docs/10 §8.8](./docs/10-workflow-git.md)) et `delete_branch_on_merge` est un **réglage du dépôt qu'aucun script ne pose** — posé à `true` le 2026-08-19 (#384), après que son absence eut laissé s'accumuler 22 branches distantes : GitHub n'a pas d'équivalent par PR du `--remove-source-branch` de GitLab, donc rien dans le cycle d'un ticket ne le remplace ([docs/10 §6](./docs/10-workflow-git.md)). `doctor.sh` en surveille la dérive et imprime la commande de réparation. `bootstrap-board.sh` (colonnes du Kanban), `migrate-workflow-labels.sh` (rattrapage one-shot de #207) et `bootstrap-lifecycle.sh` (champ Status natif GitLab) ont été supprimés avec l'outillage GitLab.

## Garde-fous (autonomie sous supervision)

- Ne jamais merger ou fermer une PR automatiquement — le merge est toujours une décision humaine.
- Ne jamais force-push une branche déjà poussée.
- Ne supprimer une branche (locale ou distante) que si la forge confirme que sa PR est `merged`. Une fois cette confirmation acquise, la suppression locale se fait avec `git branch -D` (le projet merge en **squash**, donc `-d` refuserait la branche à tort) — jamais `-D` sur une branche dont le merge n'est pas confirmé par la forge.
- Avant `/ticket-start`, vérifier qu'il n'y a pas de changements non commités sur la branche courante ; sinon s'arrêter et demander quoi en faire.
- **Ne jamais clôturer un ticket que la session ne traite pas.** `/ticket-finish` et `/ticket-ship` passent `bash scripts/gitlab/lib.sh close-guard <iid>` **avant toute écriture** (commit, push, PR, statut, temps) et s'arrêtent si la branche courante porte un **autre** ticket (`3`), si le ticket est assigné à **quelqu'un d'autre** (`4`) ou si la branche ne porte aucun iid (`5`) ; un ticket illisible (`1`) est signalé sans bloquer. Le contrôle **fort** est local (iid ↔ nom de branche) — la propriété du ticket ne l'attrape que s'il est assigné à une personne nommée, l'équipe partageant un même compte de forge. Refus **franchissable uniquement sur demande explicite** de l'utilisateur (reprise assumée d'un ticket laissé en plan), jamais en silence, et rappelé dans le résumé de clôture ([docs/10 §6](./docs/10-workflow-git.md)).
- `/ticket-ship` ne committe **jamais sur `main`** et refuse un arbre **vide ou en conflit** ; comme toutes les commandes, il ne merge, ne ferme, ni ne force-push jamais. Ces règles sont désormais aussi **adossées à la couche permissions** ([`.claude/settings.json`](./.claude/settings.json) : `deny` sur force-push, `gh pr merge`/`pr close` et `gh run delete`) — un filet de sécurité, pas un remplacement du jugement de l'agent.
