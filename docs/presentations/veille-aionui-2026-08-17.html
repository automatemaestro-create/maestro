Le paysage

Quatre dépôts, et la date de création raconte l'histoire

Analyser « le repo AionUi » seul mène droit à un contresens : le dépôt qu'on clone ne contient plus la boucle d'agent. Elle a été extraite dans un binaire séparé en avril 2026, huit mois après le lancement du produit.

Le produit a un an. Le noyau Rust en a quatre mois, et le CHANGELOG d'AionUi ne remonte pas plus loin que 2.1.4 (27 mai 2026) : la réécriture a réinitialisé l'historique visible. Chaque version d'AionUi épingle une version de noyau ("aioncoreVersion": "v0.1.68" dans le package.json), et le binaire est téléchargé depuis les releases d'AionCore au moment du packaging, par plateforme et par architecture.

Autrement dit : ils ont d'abord construit le produit en TypeScript dans Electron, puis ont sorti le moteur de la coquille. C'est exactement le mouvement inverse de celui qu'on fait quand on part d'une bibliothèque et qu'on lui ajoute une interface.

Axe 1 — Frontière d'exécution

La fenêtre n'exécute rien

C'est la découverte structurante, et celle qui parle le plus fort à notre ticket #350.

Le processus principal Electron résout un binaire nommé aioncore — via la variable AIONUI_BACKEND_BIN, sinon dans resources/bundled-aioncore/{plateforme}-{arch}/, sinon dans le PATH —, le lance, surveille sa santé, et rend son port. Tout le reste de l'application, y compris le processus principal lui-même, parle à ce démon en HTTP REST + WebSocket sur 127.0.0.1 (repli :13400). Le fichier qui porte ça, common/adapter/httpBridge.ts, se décrit comme un « drop-in replacement » du pont IPC local : les mêmes appels, routés ailleurs.

Conséquence directe, et assumée : la même interface React tourne dans un navigateur, servie sur le réseau local par le paquet web-host, qui fait reverse-proxy de /api/* et upgrade /ws vers le même démon. Le mode bureau et le mode WebUI ne sont pas deux produits : ce sont deux clients du même serveur.

Une nuance qu'il faut poser

Maestro a deux systèmes d'agents, et les confondre fausse toute comparaison. Le premier est le produit (maestro/engine, orchestrator, queue, durable) — c'est lui qui se compare à AionCore. Le second est l'outillage de développement (scripts/orchestrate, les commandes /ticket-*) : un pilote shell qui lance des sessions Claude Code sur notre propre backlog. AionUi n'a pas d'équivalent du second — leur workflow de développement est du Claude Code ordinaire, cadré par des skills (on y revient plus bas).

Cela dit, sur la question de la survie d'un run, c'est bien le pilote qui est notre pendant. Et il a fait le même choix qu'AionUi, pour la même raison : le pilote est un script shell dans une console indépendante (run.sh --detach), jamais une session Claude Code — parce qu'une boucle hébergée par une session consomme le quota qu'elle pilote et meurt avec elle. AionUi formule la même contrainte autrement : leur superviseur est le processus Electron, mais ce qu'il supervise est un binaire qui ne dépend d'aucun runtime installé.

Ce que ça dit pour Maestro

La question du #350 — « quelle frontière d'exécution pour qu'un run survive à son hôte ? » — a chez eux une réponse nette : un binaire, un port, un protocole. Le prix payé est visible dans le dépôt et il n'est pas anodin : résolution du binaire par plateforme × architecture, diagnostics de démarrage, détection d'incompatibilité de runtimeKey, réparation de base corrompue, dialogue dédié quand la base a été écrite par une version plus récente. Ce sont trois fichiers de process/startup/ qui n'existent que parce que le moteur est un processus séparé qu'on peut rater.

Ce qui est transposable n'est pas Rust, c'est la discipline du contrat : leur crate d'API (aionui-api-types) a interdiction de dépendre d'Axum ou de quoi que ce soit de HTTP. Le contrat est une source unique, indépendante du transport — ce qui leur permet précisément d'avoir le même client en Electron, en navigateur et en CLI.

Axe 2 — Le système d'agents

Ils abstraient les agents ; nous abstrayons les modèles

C'est la différence conceptuelle la plus profonde entre les deux projets, et elle explique presque tout le reste.

AionUi détecte les CLI installés sur la machine (which sur une liste POTENTIAL_ACP_CLIS) et les pilote tous par le même protocole : ACP (Agent Client Protocol), avec ses méthodes session/new, session/load, session/resume, session/prompt. Claude Code, Codex, Gemini CLI, Qwen, Goose, OpenCode, Cursor Agent, Copilot, Droid, Kimi… et, détail qui compte, leur propre agent intégré : aionrs est lui aussi un CLI, joint par le même chemin. Ils n'ont pas gardé de voie privilégiée pour leur moteur maison.

Maestro abstrait un cran plus bas. ModelProvider (providers/claude.py, openai_compat.py) rend l'exécution outillée agnostique du fournisseur de modèle ; l'agent, lui, est décrit chez nous par un RoleProfile — identité, modèle, outils, prompts — et c'est notre runtime qui tient la boucle. Nous fabriquons nos agents ; eux les branchent.

AionUi — brancher

L'unité est le processus agent. Ce qui varie d'un agent à l'autre est décrit en base (table agent_metadata) : commande, capacités MCP, répertoire de skills natif.

  • Ajouter un agent = une ligne de métadonnées + un adaptateur ACP
  • Le prompt système, les outils, la boucle : chez l'agent, pas chez eux
  • Rançon : ils héritent des différences de chacun — modes de permission, hot reload des skills, sandbox Codex… documentées agent par agent

Maestro — fabriquer

L'unité est le rôle. Un RoleProfile déclare l'identité, le modèle, les outils, les trois fragments de prompt et le plafond de tours ; le runtime générique fait le reste.

  • Ajouter un agent = déclarer un profil, sans copier de code
  • Le comportement est le nôtre de bout en bout — garde-fous, sandbox jetable, mesure d'usage
  • Rançon : rien n'arrive gratuitement de l'écosystème ; chaque capacité se code

Aucune des deux positions n'est meilleure dans l'absolu — elles répondent à des promesses différentes. AionUi vend « vos agents, dans une seule fenêtre » : l'hétérogénéité est le produit. Maestro vend une équipe d'agents cohérente sur un objectif : l'homogénéité est le produit. Mais il y a un point où leur choix est instructif pour nous : ils ont fait passer leur propre moteur par le protocole public. C'est la version exécutable de notre principe d'agnosticisme — on ne peut pas prétendre qu'un connecteur est de première classe si le moteur maison prend un raccourci que personne d'autre n'a.

Axe 3 — Teams et « team members »

Une équipe est un serveur MCP

C'est la pièce la plus intéressante du système, et la plus proche de ce que nous construisons.

Le vocabulaire d'abord, parce qu'il est précis. Une équipe est composée de slots : un slot (slot_id) est une instance de membre, pas un assistant. Le même assistant peut être recruté deux fois dans une équipe — deux slots, deux conversations, deux sessions indépendantes. Le premier slot est le Leader (role: 'leader') : il ne peut être ni retiré, ni déplacé, ni éteint, et le backend refuse en dur un team_shutdown_agent qui le viserait. Les autres sont des teammates, dont le statut est un cycle de vie explicite — pending · idle · active · completed · failed · dormant.

Le mécanisme, ensuite. Au démarrage d'une session d'équipe, le backend ouvre un serveur MCP dédié à cette équipe sur un port local aléatoire, et injecte à chaque membre sa configuration de connexion. L'agent s'authentifie par une poignée de main JSON-RPC initialize(auth_token, slot_id) — et c'est ce slot_id mémorisé qui sert ensuite à décider si l'appelant a le droit d'appeler un outil réservé au Leader. La collaboration entre agents ne passe par aucun canal privé : elle passe entièrement par ces outils.

Le détail que je n'attendais pas : le protocole social est dans la description de l'outil

La description de team_spawn_agent ne décrit pas ce que fait l'outil. Elle décrit une procédure d'approbation, écrite à l'impératif dans le texte que le modèle lit :

« Commence par une phrase courte expliquant pourquoi des coéquipiers supplémentaires aideraient. Dis à l'utilisateur lesquels tu recommandes. Présente la proposition sous forme de tableau : nom, responsabilité, assistant recommandé. […] Demande s'il faut les créer tels quels. Rappelle-lui dans cette question qu'il pourra plus tard te demander de remplacer n'importe quel coéquipier si l'équipe ne fonctionne pas bien. N'appelle PAS cet outil dans le même tour ; attends une approbation explicite dans un message ultérieur. »

C'est un choix de conception assumé : le garde-fou « l'humain valide le recrutement » n'est pas un verrou dans le code, c'est une consigne dans le prompt d'un outil. Il tient tant que le modèle obéit. Nous avons fait l'inverse — nos garde-fous équivalents (jamais de merge automatique, jamais de force-push, close-guard avant toute écriture) sont adossés à la couche permissions et à des codes de retour, précisément parce qu'un prompt est une prière et pas une barrière. Leur approche a l'avantage de la souplesse et l'inconvénient exact qu'on imagine.

Face à Maestro : le plan avant, ou le plan pendant

Sur la mécanique, la convergence est frappante et me semble non fortuite : nous avons nous aussi une boîte aux lettres inter-agents (maestro.messaging.mailbox, ticket #44 — Redis Pub/Sub ou en mémoire, avec journalisation dans la télémétrie), un handoff observable qui ne débloque l'aval qu'à réception, et un tableau noir léger où chaque tâche reçoit les résultats de ses dépendances. Deux équipes qui n'ont pas discuté ont abouti aux mêmes trois primitives.

La divergence est ailleurs, et elle est de fond. Chez AionUi, le plan est produit à l'exécution par un modèle : le Leader reçoit l'objectif, décide du découpage, crée les tâches par appel d'outil, recrute au besoin. Chez Maestro, le plan est produit avant, et validé : l'orchestrateur rend un JSON contrôlé contre task.schema.json, le routeur assigne, le moteur exécute le DAG en parallélisant ce qui est indépendant, et un échec bloque explicitement l'aval au lieu de laisser des exécutions orphelines. Le brief (#318) va plus loin encore : il rend approuvable par un humain le cadrage avant toute exécution payante.

Délégation à l'exécution

  • S'adapte à l'imprévu — le Leader recrute un profil qu'on n'avait pas anticipé
  • Aucune structure à maintenir : le plan est du texte dans une conversation
  • Mais rien n'est vérifiable avant de payer : pas de schéma, pas de coût estimé, pas de point d'approbation naturel
  • Et les cycles sont possibles — A blocked_by B et B blocked_by A sont acceptés par le tableau

Plan validé en amont

  • Un plan invalide est rejeté avant le premier appel outillé
  • L'ordre topologique rend le rapport déterministe, indépendant de l'ordre d'achèvement
  • Un point d'approbation humain existe naturellement : le brief
  • Mais on paie la rigidité : ce que le plan n'a pas prévu, la boucle ne l'invente pas en cours de route
Ce que ça dit pour Maestro

Deux idées m'ont paru directement transposables, sans toucher au modèle « plan validé ».

Le slot. Séparer « quel assistant » de « quelle instance » est une distinction que nous n'avons pas, et qui règle proprement le cas « deux développeurs sur ce run ». Chez eux c'est ce qui porte la couleur d'identité, la conversation, le statut, les permissions en attente.

Le tableau de tâches comme surface partagée écrivable par les agents. Notre tableau noir est en lecture pour l'aval ; le leur est un objet de première classe que chaque agent lit et modifie, et qui est aussi ce que l'humain regarde. C'est ce qui leur permet de rendre une vue d'activité unifiée — messages et tâches sur la même frise, rangés par couloir de membre — là où nous n'avons de visibilité qu'en fin de run.

Axe 4 — MCP

Deux mécanismes d'injection, et un redémarrage de processus assumé

AionUi distingue nettement les serveurs MCP de l'utilisateur — configurés dans les réglages, persistés en base, avec test de connexion et OAuth — et les serveurs de session, générés dynamiquement, dont le serveur d'équipe est le cas d'usage. Les deux sont fusionnés au moment du session/new de l'agent.

Le point technique qui mérite d'être connu : la liste des outils MCP est figée à la création de session, elle n'est pas rechargeable à chaud. Comme le serveur d'équipe n'existe qu'au démarrage de l'équipe (port et jeton inconnus avant), ils tuent et recréent le processus agent — en gardant la conversation identique et en s'appuyant sur le resume de chaque backend pour retrouver le contexte. Le principe est écrit noir sur blanc dans leur doc : « conversation inchangée + processus agent redémarré + session reprise ». C'est une contrainte du protocole, pas un contournement, et elle vaut pour n'importe qui voudrait injecter un MCP après coup.

Chez nous, le modèle est plus statique mais plus déclaratif : le pool projet (core/mcp/pool.json) déclare une intégration une fois, les activations par agent la branchent, et le montage se fait à chaud à chaque tâche — l'exécuteur relit le dépôt à chaque exécution. Deux différences notables en notre faveur : les secrets voyagent en références ${VARIABLE} résolues au montage, jamais en clair dans un fichier versionné ; et un serveur déclaré "optionnel": true s'omet du montage au lieu de faire échouer la tâche. Une différence en leur faveur : ils ont l'OAuth interactif et le test de connexion depuis l'UI, nous pas encore.

Axe 5 — Skills

Le format de Claude, généralisé à vingt agents

Les skills d'AionUi sont des dossiers avec un SKILL.md à front-matter — le format de Claude Code, repris tel quel — importables depuis un dossier ou un zip. Trois étages : intégrées (livrées avec l'app), utilisateur, et contribuées par des extensions. Le contrôle est par conversation : un indicateur dans l'en-tête du chat montre les skills actives, avec recherche et exclusion.

L'intéressant est la stratégie de livraison, parce qu'elle affronte un problème réel : chaque agent range ses skills ailleurs, et ACP ne dit rien du sujet. Leur réponse est une colonne en base, native_skills_dirs, remplie agent par agent. Quand elle est renseignée, ils lient les skills dans le workspace au bon endroit et laissent l'agent les découvrir nativement. Quand elle est vide, ils basculent sur une injection de prompt au premier message — un index des skills, ou leur contenu complet en mode avancé.

Ils documentent aussi leur propre limite avec une honnêteté qui mérite d'être notée : la liste des skills d'une session est un instantané figé à la création (extra.skills, que le backend refuse de modifier ensuite), si bien que « ajouter une skill en cours de conversation » n'est pas réellement supporté au niveau produit, même quand l'agent sous-jacent saurait le faire.

Le renversement, côté Maestro

Chez nous, les skills sont un outil de développement : .claude/skills porte /ticket-start, /orchestrate, /verify, /banc-mise-en-page — la façon dont nous travaillons sur Maestro. L'équivalent produit chez nous s'appelle playbook (maestro/agents/playbooks.py, relu à chaud à chaque tâche). Chez AionUi, les skills sont un produit, avec un catalogue de 21 assistants et des skills intégrées (pptx, docx, pdf, xlsx, mermaid) — et leur propre workflow de développement, lui, tient dans quatre skills très sobres.

Leurs quatre skills de développement, pour comparaison

architecture — un arbre de décision « où va ce code ? », les règles dures de frontière entre processus (le renderer n'importe pas fs, le main n'importe pas le DOM), les conventions de nommage, et deux règles structurelles inhabituelles : maximum 10 enfants directs par répertoire et pas de répertoire à fichier unique. i18n — obligation de clé pour tout texte visible. testing — Vitest, seuil de couverture 80 %. bump-version — la procédure de release.

Leur AGENTS.md encode surtout de la structure (où, comment nommer, quelles frontières) ; notre CLAUDE.md encode surtout du processus (cycle de vie d'un ticket, règles git, qui merge). Ce sont deux réponses au même problème — apprendre le dépôt à l'agent — sur deux axes différents. Détail amusant : ils interdisent explicitement les signatures d'IA dans les commits (« NEVER add Co-Authored-By »), là où nous les imposons.

Axe 6 — La question du bureau

Pourquoi une application de bureau ?

La réponse courte : parce que l'agent travaille sur vos fichiers, avec vos CLI, sur votre machine. La réponse longue est plus intéressante, parce que le code montre qu'ils ont commencé à en sortir presque aussitôt.

Cinq raisons se lisent directement dans le dépôt, et aucune n'est esthétique :

  1. L'accès aux fichiers locaux est le produit. La promesse est « Cowork » — l'agent lit, écrit, range, génère des .pptx et des .xlsx dans vos dossiers. Un service distant ne peut pas le faire sans que vous téléversiez tout.
  2. Lancer des processus locaux demande un hôte local. Claude Code, Codex, Gemini CLI sont des binaires sur la machine. Le noyau y consacre une infrastructure entière : un Node managé qu'ils embarquent, une reconstruction du PATH à partir du shell de connexion (parce qu'une app lancée depuis le Dock n'hérite pas du PATH du terminal), un constructeur de sous-processus qui pose kill_on_drop et nettoie NODE_OPTIONS.
  3. La distribution. Une app installable est ce que le public visé sait installer. Le dépôt en porte tout le poids : electron-builder, notarisation macOS, Squirrel Windows, Homebrew, mise à jour automatique avec refus des rétrogradations, et des tests de fumée pour les messages d'erreur de l'installeur.
  4. L'intégration système. Liens profonds aionui://, instance unique, identité d'application Windows, récupération après crash GPU, mascotte de bureau, notifications, menu natif.
  5. La confidentialité comme argument. « Tout est stocké localement dans une base SQLite. Rien n'est téléversé. » C'est une ligne de leur FAQ, et c'est vérifiable dans l'architecture.

Et pourtant. Le même dépôt contient un mode WebUI complet, un accès distant par le réseau local ou par Internet, une connexion par QR code, et des passerelles Telegram, Lark, DingTalk et WeChat. Leur propre FAQ répond « oui » à « peut-on le faire tourner sur un serveur sans écran ? ».

La conclusion que j'en tire

Le bureau, chez eux, est un choix de distribution, pas un choix d'architecture. Ils ont commencé par livrer une app Electron parce que c'est ce qu'on peut demander à quelqu'un d'installer, puis ils ont extrait le moteur pour pouvoir le faire tourner n'importe où — et c'est cette extraction, pas la fenêtre, qui est la décision d'architecture.

Ce que ça vaut pour nous : la question « faut-il une app de bureau pour Maestro ? » est mal posée tant que le moteur n'a pas de frontière propre. Une fois qu'il en a une — le sujet du #350 — l'emballage bureau devient une option de distribution qu'on prend ou pas, et le coût est mesurable : chez eux, une bonne moitié de process/startup/ et une famille entière de tests de fumée n'existent que pour ça.

Trois choses m'ont retenu l'attention, au-delà du choix de Rust.

Le miroir de CI est une contrainte, pas une invitation. Chez eux, just push enchaîne lint → format → typage → tests → git push, et tout échec annule le push. Nous avons le filet équivalent (scripts/ci/local.sh) mais nous l'invoquons ; eux l'ont mis sur le chemin. Détail qui compte pour un agent : leur AGENTS.md prend soin de préciser que le dépôt a beaucoup d'avertissements de lint préexistants et qu'il faut juger sur le code de retour, pas sur le volume de sortie — exactement le genre de piège qui envoie une session autonome réparer ce qui n'est pas cassé.

La revue de PR est faite par un modèle, en CI. Deux workflows GitHub Actions (gpt-review et gpt-pr-assessment), plus du tri automatique des tickets et des discussions. Ils font tourner un agent sur leur propre flux de contributions — ce qui, avec 3 286 forks et 822 tickets ouverts, ressemble moins à un gadget qu'à une nécessité.

Les PRD sont dans le dépôt, en chinois, avec l'état d'implémentation par fonctionnalité. Le fichier ACP liste 51 points numérotés avec, pour chacun, « implémenté / partiellement / non » et la raison des tests E2E marqués skip. C'est le même instinct que nos docs docs/10 — écrire le pourquoi à côté du code — appliqué au produit plutôt qu'au processus.

Bilan

Ce que je retiendrais, et ce que je laisserais

À creuser

  • Le contrat d'API sans dépendance transport. Leur crate de types ne connaît pas HTTP ; c'est ce qui rend possible d'avoir le même client en fenêtre, en navigateur et en ligne de commande.
  • La notion de slot — instance de membre distincte de l'assistant, porteuse de la conversation, du statut et des permissions en attente.
  • Le tableau de tâches écrivable par les agents, doublé d'une vue d'activité unifiée messages + tâches par couloir de membre. C'est notre angle mort en cours de run.
  • Le filet local sur le chemin du push, plutôt qu'à côté.
  • ACP comme protocole d'intégration d'agents tiers — à connaître, même si nous ne l'adoptons pas : c'est en train de devenir la prise standard.

À ne pas importer

  • Le garde-fou par consigne de prompt. Leur approbation humaine avant recrutement tient parce que le modèle est docile. Nos règles équivalentes sont adossées à la couche permissions ; c'est plus rigide et c'est le but.
  • La délégation intégrale du plan au Leader. Elle coûte la vérifiabilité — pas de schéma, pas de point d'approbation avant dépense, et un tableau de tâches qui accepte des dépendances circulaires.
  • L'emballage bureau tant que la frontière d'exécution n'est pas tranchée. C'est la conséquence, pas la cause.
  • L'hétérogénéité comme produit. Brancher vingt agents veut dire hériter de vingt comportements de permissions, de vingt conventions de skills et de vingt façons de reprendre une session. Leur documentation en porte la trace, agent par agent.

La phrase à retenir

AionUi et Maestro ne sont pas concurrents : ils répondent à deux questions différentes. « Comment donner à une personne une fenêtre sur tous les agents installés sur sa machine ? » contre « comment faire produire à une équipe d'agents un résultat vérifiable sur un objectif donné ? ». Mais ils se rejoignent sur trois primitives — boîte aux lettres, tableau partagé, machine à états de réveil — et sur une même décision d'architecture, prise à des moments différents : sortir le moteur du processus qui l'affiche. Eux l'ont faite en avril. C'est notre #350.
